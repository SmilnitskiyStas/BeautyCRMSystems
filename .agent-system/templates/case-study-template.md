# Case Study Template

**Джерело:** структура кейсу, адаптована з практики документування проєктних кейсів
**Використання:** заповнити один екземпляр на проєкт (`content/projects/{slug}.md` або еквівалент — залежно від обраного рішення для контент-шару, див. відповідний ADR проєкту). Кожне текстове поле заповнюється окремо для `uk` і `en` — без автоматичного машинного перекладу під час завантаження сторінки. Не вигадувати неіснуючі факти, клієнтів чи цифри.

---

### 1. Назва
_Назва проєкту/продукту, як вона показується в UI._

### 2. Коротка ціннісна пропозиція
_Одне-два речення: що це і яку користь дає бізнесу. Показується в картці кейсу в списку проєктів._

### 3. Статус проєкту
_Concept / MVP / In Development / Internal Product / Prototype — чесно, без видавання концепту за запущений клієнтський продукт._

### 4. Тип проєкту
_Категорія фільтра в списку проєктів: Websites / Web Applications / SaaS / CRM/ERP / Mobile / AI / Automation / Internal Products / Concepts._

### 5. Індустрія
_Приклад галузей — адаптувати під власну ЦА: Retail / Restaurants / Healthcare / Beauty / Construction / Logistics / Education / Startups / Local Business — або інше; звʼязати з `/industries/[slug]`, якщо існує відповідна галузева сторінка._

### 6. Роль команди
_Що саме робила команда в цьому проєкті: дизайн, frontend, backend, mobile, AI, повний цикл._

### 7. Проблема
_Яку бізнес-проблему або задачу мав клієнт до старту проєкту._

### 8. Цілі
_Вимірювані або описові цілі проєкту._

### 9. Обмеження
_Технічні, часові, бюджетні або організаційні обмеження, що вплинули на рішення._

### 10. Дослідження
_Що досліджували перед вибором рішення: користувачів, конкурентів, наявні процеси._

### 11. Запропоноване рішення
_Загальний опис підходу до вирішення проблеми (до деталей архітектури/UX/UI нижче)._

### 12. Інформаційна архітектура
_Структура розділів/екранів продукту, ключові user flows._

### 13. Основні функції
_Список ключових функцій/можливостей продукту._

### 14. UX-рішення
_Ключові рішення щодо взаємодії та користувацького досвіду і чому саме так._

### 15. UI-рішення
_Ключові візуальні/інтерфейсні рішення (стиль, компоненти, патерни)._

### 16. Технічна архітектура
_Огляд архітектури: шари, сервіси, потоки даних._

### 17. Технології
_Конкретний стек: frontend / backend / DB / infra / mobile / AI — відповідно до технологічного стеку проєкту._

### 18. Безпека
_Які заходи безпеки застосовано (auth, валідація, ізоляція даних, secrets тощо)._

### 19. Інтеграції
_Сторонні сервіси/API, з якими інтегроване рішення._

### 20. Оптимізація продуктивності
_Що конкретно зроблено для швидкодії. Без вигаданих метрик — лише підтверджені або описові покращення._

### 21. Результат
_Якщо немає підтверджених цифр — описові результати: скорочення кількості ручних операцій, централізація даних, автоматизація сповіщень, покращення контролю, спрощення роботи персоналу, єдиний інтерфейс. **Не вигадувати бізнес-результати.**_

### 22. Наступні етапи
_Що заплановано далі для цього проєкту (roadmap), якщо застосовно._

### 23. Галерея
_Перелік зображень/mockups: шлях до файлу + alt-текст (обидві локалі) для кожного зображення._

### 24. CTA
_Заклик до дії в кінці кейсу — напр. «Обговорити подібний проєкт», з посиланням на `/start-project` або `/contact`._
