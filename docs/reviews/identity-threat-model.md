# Review: threat-model контракту §31 «Глобальна ідентичність» (ADR-024)

**Date:** 2026-11-17 · **Reviewer:** security-reviewer · **Task:** TASK-860 · **Verdict:** approved-with-notes (critical немає)

Об'єкт: `.claude/docs/beauty-contracts.md` §31 (API-CONTRACT-IDENTITY-V1), ADR-024. Модель «ідентичність ≠ членство», deny-all RLS і доступ лише через `SECURITY DEFINER` надійні; токени прив'язані до tenant, `switch` бере ідентичність із сервера, квиток входу в httpOnly-cookie. Прямого IDOR між бізнесами немає. Нижче скорочений виклад знахідок (повна версія була у звіті агента).

## Знахідки

- **F-1 [high] Ліміт `auth` через BFF спільний для всіх (staging).** API бачить IP контейнера `web` для кожного користувача (`docker-compose.staging.yml:80`, `Beauty__TrustedProxies` містить лише шлюз), `X-Forwarded-For` від BFF ігнорується. 10 запитів/хв без автентифікації дають 429 усім. Виправлення: статична адреса `web` у мережі, додати її в `TrustedProxies`, BFF пересилає XFF від reverse proxy; smoke-тест двох клієнтських IP; без цього реліз TASK-866 заблоковано.
- **F-2 [medium] Блокування — оракул існування пошти.** Лічильник наявної ідентичності в БД не згасає, невідомої пошти в пам'яті згасає, скидається при рестарті/витісненні. Варіант A (рекомендований): єдина таблиця `auth_login_attempts` (ключ = HMAC(pepper, email)), однакова семантика вікна для всіх шляхів. Варіант B: мінімум із `last_failed_at` і задокументованим залишковим ризиком. Рішення впливає на схему — до TASK-862.
- **F-3 [medium] `password/forgot` — оракул за часом (запис у БД лише для наявної пошти).** `202` до роботи з БД, пошта в обмежену in-process чергу, `auth_password_reset_issue` повертає `void`.
- **F-4 [medium] Самоприйняте запрошення займає чужу пошту на всій платформі** (запрошувач тримає токен, ідентичність створюється без доказу володіння скринькою; Q11 — пошта лишається зайнятою). Варіанти: 1) прийняти ризик + аудит `identity.created`, ліміт створених ідентичностей на tenant, процедура оператора; 2) `email_verified_at` і спрощене звільнення непідтверджених; 3) V2: лист запрошення на адресу запрошеного. Потрібне продуктове рішення.
- **F-5 [medium] Злиття дублікатів + `switch`**: сесія «програвшого» членства з живим refresh входить без пароля в бізнес «переможця». Виправлення: при злитті відкликати refresh усіх злитих членств; злиття лише за явним allowlist (`email_key` з preflight), не глобальним прапорцем.
- **F-6 [low]** Access-токен живе до 15 хв після скидання пароля. Виправлення: `users.sessions_valid_after`, перевірка `iat` у `AccessContextMiddleware` (рядок `users` уже читається щоразу) і в refresh.
- **F-7 [low]** Різниця в часі «правильний пароль без членств» практично невимірна на тлі bcrypt; штучну затримку не додавати.
- **F-8 [low] Посилення SECURITY DEFINER/grants для TASK-862:** REVOKE нових глобальних таблиць після `GRANT ON ALL TABLES` для app/worker/PUBLIC; явні REVOKE/GRANT EXECUTE для кожної `auth_*`; стартова перевірка за зразком DbRoleGuard; `RETURNS TABLE` з явними колонками; нормалізація пошти всередині функцій; consume одним `UPDATE … RETURNING`; без `CREATE` на схемі `public`; жоден DTO/вхід не містить `identity_id`.
- **F-9 [low]** Сирий токен скидання в БД до відправки: краще генерувати у воркері й зберігати лише sha256; інакше `FOR UPDATE SKIP LOCKED`, жодної функції для app, що повертає токен, обнулення при purge.
- **F-10 [low]** Посилання скидання будувати лише з конфігу (не з Host); лист «Пароль змінено»; тихий ліміт на пошту — прийнятий ризик.
- **F-11 [low]** `switch`: перечитати членство цілі під `UseTenant(target)` (TOCTOU); frontend після switch очищає кеші.
- **F-12 [info]** Блокування діє на всі бізнеси людини (Q10 прийнято); метрика й алерт на повторні блокування.
- **F-13 [info]** Фіктивний хеш має мати той самий bcrypt cost, що й реальні; перевірити в preflight/при вході.
