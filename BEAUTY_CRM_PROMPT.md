## 1. Мета

Побудувати **Beauty CRM**: B2B-платформу для б'юті-сфери (салони, барбершопи, косметологи, мережі закладів).

Що має вміти:
1. CRM: клієнти, історія візитів, нотатки, вподобання, лояльність.
2. Календар майстрів, де запис займає стільки часу, скільки триває послуга.
3. Послуги й ціни, запуск акцій (знижка, заклади, послуги, терміни).
4. Для мережі: клієнт обирає **заклад** і **спеціаліста**; ціни можуть відрізнятися по закладах.
5. Онлайн-запис клієнта: заклад, майстер, послуга, час, оформлення (нагадування, оплата карткою або готівкою, умови скасування).
6. Канали зв'язку: Telegram, Instagram, Facebook Messenger, WhatsApp, Viber, віджет на сайті. Записи й повідомлення з каналів.
7. **AI-асистент для бізнесу**: обробляє заявки, спілкується з клієнтами, допомагає з акціями (ціна, текст, кому надіслати), працює в каналах з регульованою автономністю.
8. Аналітика: мережа, заклади, спеціалісти, акції.

## 2. Припущення (підтвердь у gate перед стартом)

- **A1. Стек і місце в коді:** Beauty CRM будується як нові модулі **того ж модульного моноліту** (див. `CLAUDE.md`): Next.js + ASP.NET Core .NET 8 + PostgreSQL 16 (RLS, multi-tenant) + BullMQ worker + Claude API. Тип бізнесу `tenants.business_type = 'beauty'`, нові ендпоінти захищені `[RequireModule("beauty_*")]`. Якщо потрібен окремий репозиторій, змінити лише шляхи.
- **A2. Правило скасування:** скасування запису за 12 годин до візиту повертає 50% оплаченої суми. Трактування (за 12 год **і менше** чи **саме** за 12 год) підтвердити.
- **A3. Платіжний провайдер:** не обрано. Реалізувати через інтерфейс `IPaymentService` без прив'язки до провайдера, картка = онлайн-передоплата, готівка = оплата в закладі.
- **A4. Нагадування:** варіанти «не нагадувати», «за 1 год», «за 2 год».
- **A5. AI-модель:** `claude-sonnet-4-5` через Anthropic SDK, ізольовано в `ShelfGuard.Infrastructure/AI`.
- **A6. Канали:** Meta (Instagram, Facebook, WhatsApp) вимагають app review та бізнес-верифікації. На етапі розробки використовувати mock-адаптери, реальні токени лише через `.env`.

## 3. Gate: питання користувачу ДО запуску агентів

Головна сесія ставить ці питання через `AskUserQuestion` і чекає відповіді. Агенти не можуть уточнювати в процесі.

1. Підтвердити A1 (той самий моноліт) чи окремий репозиторій.
2. Правило скасування й повернення коштів (A2): які саме межі часу, повернення на картку чи на баланс.
3. Платіжний провайдер, якщо вже відомий.
4. Які канали в пріоритеті для першого релізу (рекомендація: Telegram + Instagram + віджет на сайті).
5. Режим AI за замовчуванням у каналах: «Тільки підказує», «Готує, я підтверджую» (рекомендовано) чи «Відповідає сам».

Якщо відповіді відсутні, застосовувати рекомендації з цього файлу й записати рішення в task log.

## 4. Агенти та їхні особисті Skills

Кожен агент має **власний Skill** і читає його першим. Skills лежать у `.claude/skills/<skill>/SKILL.md`.
Агенти спавняться як `general-purpose` і вказують на свій role-файл у `.claude/agents/` (див. `CLAUDE.md`, розділ «How to spawn an agent»). Ролі `integrations-developer` та `ai-agent-developer` нові: створити role-файли за зразком `.claude/agents/backend-developer.md`.

## 5. Skills: вміст кожного (створити у Кроці 1)

Формат кожного файлу: frontmatter `name`, `description`, потім стислі правила (до ~40 рядків). Нижче змістовне ядро.

### `beauty-schema` (агент 1)
- Таблиці: `beauty_locations`, `beauty_specialists`, `beauty_specialist_locations` (графік по закладах), `beauty_services`, `beauty_service_prices` (ціна мережі + override по закладу), `beauty_appointments`, `beauty_clients`, `beauty_client_notes`, `beauty_promotions` (+ `_locations`, `_services`), `beauty_channels`, `beauty_conversations`, `beauty_messages`, `beauty_ai_actions` (журнал дій AI), `beauty_reminders`, `beauty_payments`.
- Кожна таблиця має `tenant_id` і RLS-політику з `NULLIF(current_setting(...), '')` (див. `CLAUDE.md`).
- `beauty_appointments`: `starts_at`, `duration_minutes` (береться з послуги на момент запису), `status` (`pending`, `confirmed`, `completed`, `cancelled`, `no_show`), `source` (`admin`, `online`, `telegram`, `instagram`, ...), `price_original`, `price_final`, `promotion_id`.
- Запобігання перетину записів майстра: exclusion constraint або перевірка в транзакції.
- Секрети каналів зберігати зашифрованими, у відповіді API маскувати (останні 4 символи).
- Нові міграції не змінюють існуючі таблиці ShelfGuard деструктивно.

### `beauty-booking-api` (агент 2)
- Тонкі контролери, логіка в `Application/Features/Beauty*`.
- Ендпоінти: розклад вільних слотів (з урахуванням тривалості послуги й графіка по закладах), створення/перенесення/скасування запису, CRUD послуг і цін, акції (розрахунок ціни зі знижкою, обмеження по закладах і послугах), клієнти й історія, аналітика (мережа, заклад, акції).
- Скасування: розрахунок повернення за правилом A2 в окремому сервісі з тестами.
- Нагадування: при створенні запису планувати `beauty_reminders` за вибором клієнта.
- Оплата через `IPaymentService`, не прив'язуватись до провайдера.
- Валідація лише на межах (API, зовнішні інтеграції).

### `channels-integrations` (агент 3)
- Єдиний інтерфейс `IChannelAdapter` (прийом webhook, відправка, перевірка підпису). Адаптери: Telegram (Bot API), Instagram та Facebook Messenger (Meta Graph API), WhatsApp Business, Viber, віджет сайту.
- Вхідні повідомлення нормалізуються в `beauty_conversations` / `beauty_messages` і кладуться в чергу; вихідні йдуть через outbox з ретраями.
- Перевіряти підписи webhook; токени лише з `integration_configs`/`.env`, у відповідях маскувати.
- Враховувати обмеження Meta (вікно повідомлень, шаблони) і правила Telegram.
- На час розробки реалізувати `Mock*Adapter` для всіх каналів.
- Налаштування каналу: `inbox`, `booking`, `ai`, `mode`, `greeting`, правила передачі менеджеру (як в `Integrations.dc.html`).

### `ai-business-assistant` (агент 4)
- Увесь код Claude API, промпти й tool-визначення лише в `Infrastructure/AI/Beauty/`. Бізнес-логіка не знає про провайдера AI.
- Інструменти агента (tools): `find_free_slots`, `create_appointment`, `get_prices`, `get_active_promotions`, `get_client_context`, `draft_reply`, `suggest_promotion`, `build_audience`. Інструменти викликають сервіси Application, не БД напряму.
- Режими автономності з прототипу: `suggest` (чернетка, надсилає людина), `confirm` (готує й створює запис після підтвердження), `auto` (діє сам у межах правил).
- Обов'язково: журнал дій у `beauty_ai_actions` (що, кому, коли, можливість скасувати), правила й межі (макс. знижка, години розсилок), передача менеджеру при скарзі, питанні про оплату й проханні про людину.
- Допомога з акцією: пропозиція знижки з поясненням, таблиця цін до/після, текст оголошення, сегменти клієнтів (не були 60+ днів, VIP, нові, усі) з кількістю.
- Розсилки лише клієнтам зі згодою; поважати години розсилок і відписку.
- Тести з мокнутим клієнтом AI, без реальних викликів у CI.

### `beauty-worker-jobs` (агент 5)
- BullMQ-джоби в `worker/src/jobs/beauty-*`: надсилання нагадувань (за 1 і 2 години), outbox повідомлень з ретраями ×3, виконання кампаній-розсилок по сегментах, нагадування «давно не були», запит відгуку після візиту.
- Ідемпотентність (повторний запуск не дублює повідомлення), логування в `notification-log`.

### `beauty-admin-ui` (агент 6)
- Feature-структура `frontend/features/beauty-*`: `types.ts`, `api/`, `hooks/`, `components/`. React Query для серверного стану, Zustand лише для UI.
- Екрани: Огляд, Календар (блок = тривалість послуги, легенда типів записів), Клієнти й профіль, Спеціалісти й профіль, Ціни та акції, Аналітика, AI-асистент, Канали.
- Бічне меню зліва, однакове на всіх екранах; плаваюча іконка AI внизу праворуч з вікном (аналіз і діалог при наведенні), контекст залежить від екрана.
- Доступність: реальні `button`/`a`/`label`, цілі натискання ≥44px, контраст тексту ≥4.5:1.

### `beauty-booking-ui` (агент 7)
- Публічний mobile-first потік: заклад → майстер (або «будь-який») → послуга й час → оформлення → підтвердження.
- Оформлення: підсумок, **спадний список нагадування**, спосіб оплати (картка / готівка), блок умов скасування (50% повернення за A2), потім екран підтвердження з посиланням на запис.
- Послуги з акцією показують стару й нову ціну та мітку знижки.

### `beauty-qa` (агент 8)
- Тести бізнес-правил: перетин записів, тривалість у календарі, ціна з акцією, повернення 50%, нагадування, режими автономності AI, ізоляція tenant (RLS), webhook з невалідним підписом.
- Регресія основних сценаріїв: запис онлайн → з'являється в календарі → підтвердження → завершення.

### `beauty-security` (агент 9)
- Перевірка RLS на всіх нових таблицях, авторизації (ролі: власник, адміністратор, спеціаліст), перевірки підписів webhook, маскування секретів, захисту від prompt injection у повідомленнях клієнтів (AI не виконує інструкції з тексту клієнта), обмежень на масові розсилки, персональних даних клієнтів.

### `beauty-docs` (агент 10)
- Оновити `.claude/docs/`: доменна модель, API-контракти, схема БД, ADR по каналах і AI. Короткі task logs.

## 6. Паралельна активація

Принцип: **спочатку контракти, потім паралельна розробка по контрактах, потім збірка й перевірка.**

### Крок 1 — головна сесія (без агентів, швидко)
1. Створити `.claudeignore` (Крок 0).
2. Створити 10 skill-файлів з розділу 5 та 2 нові role-файли.
3. Записати контракти у `.claude/docs/beauty-contracts.md` (стислі): схема сутностей, список API-ендпоінтів з request/response, події черги, інтерфейси `IChannelAdapter`, `IPaymentService`, tools AI. Це єдине джерело для паралельних агентів.
4. Пройти gate (розділ 3).

### Крок 2 — залежності

```
Контракти (Крок 1)
   ├─► [1] database-engineer ─────────────► [2] backend-developer ─┐
   ├─► [3] integrations-developer (mock) ──────────────────────────┤
   ├─► [4] ai-agent-developer (fake tools) ────────────────────────┼─► інтеграція
   ├─► [5] worker-developer ───────────────────────────────────────┤
   ├─► [6] frontend admin (mock API за контрактом) ────────────────┤
   └─► [7] frontend booking (mock API за контрактом) ──────────────┘
                                                                      ├─► [8] qa-tester
                                                                      ├─► [9] security-reviewer
                                                                      └─► [10] documentation-writer
```

### Крок 3 — запуск паралельно (ОДНЕ повідомлення, кілька викликів `Agent` одночасно)

Хвиля A (старт одразу, зони запису не перетинаються): агенти **1, 3, 4, 5, 6, 7**.
Хвиля B (після завершення агента 1): агент **2**. Агенти 3–7 за потреби підключаються до реальних сервісів після B.
Хвиля C (після інтеграції): агенти **8, 9**, потім **10**.

Шаблон виклику (однаковий для кожного, змінюються роль, skill, бриф):

```
})
```

Ізоляція: зони запису агентів не перетинаються. Якщо двом агентам доводиться змінювати спільний файл (наприклад, `Program.cs`, реєстрація DI), давати одному з них `isolation: "worktree"` або виносити зміну до головної сесії.
`opus` лише для агента 1 при проєктуванні RLS і для рев'ю RLS/auth в агенті 9. З брифом: «не читай великий контекст».

## 8. Обов'язкові правила проєкту (з `CLAUDE.md`)

- Тонкі контролери; бізнес-логіка в `ShelfGuard.Application`.
- Feature-based frontend; React Query для серверного стану, Zustand лише для UI.
- AI-інтеграції ізольовані в `Infrastructure/AI`.
- RLS на кожній таблиці з tenant-даними (`NULLIF(current_setting(...), '')`).
- Секрети тільки в `.env`, у відповідях API маскувати (останні 4 символи).
- Модулі активуються через `[RequireModule("...")]` і `tenants.modules`.
- Короткі звіти: що зроблено, статус build/tests, знайдені проблеми. Без таблиць і переказу процесу.

## 9. Definition of Done

- Усі TASK-674…683 мають task log і запис у `current.md`.
- Збірка проходить: `dotnet build`, `dotnet test`, `npm run lint`, `tsc --noEmit` у змінених зонах.
- RLS-тест ізоляції tenant зелений.
- Потік «онлайн-запис → календар → нагадування» працює наскрізно на мок-каналах.
- Режим AI за замовчуванням: «Готує, я підтверджую».
- Нічого не закомічено й не запушено без прямого прохання користувача.
