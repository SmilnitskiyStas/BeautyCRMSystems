## Тон (розділ тону комунікації проєктного спеку)
Зрозумілий для власника бізнесу · конкретний · орієнтований на результат · без надмірного технічного жаргону · без шаблонних фраз · без перебільшень · без тверджень «ми найкращі» · без фейкових гарантій · без штучного keyword stuffing.

## Приклад зі спеки
Поганий варіант:
```text
Ми створюємо інноваційні рішення найвищої якості.
```

Кращий варіант:
```text
Проєктуємо та розробляємо сайти, мобільні застосунки й бізнес-системи, які автоматизують роботу, допомагають залучати клієнтів і спрощують розвиток продукту.
```

Різниця: другий варіант називає конкретний продукт і конкретну користь, перший — порожнє самозвеличення без змісту.

## Порядок подачі в кожному блоці
1. Бізнес-користь (що це дає власнику бізнесу).
2. Тільки потім — технології/спосіб реалізації.

Не міняти порядок навіть для "технічної" аудиторії (Upwork/LinkedIn клієнти теж спершу читають користь).

## Rules
- Текст живе в typed content/MDX, не хардкодиться в компоненті (розділи тону та архітектури проєктного спеку).
- Жодних вигаданих співробітників, нагород, сертифікатів, клієнтів, цифр чи відгуків (розділ достовірності контенту проєктного спеку).
- Числа (роки досвіду, кількість продуктів) — тільки реальні, редаговані через конфіг/CMS, не literal у тексті (розділ достовірних показників проєктного спеку).
- Нове поле форми, CTA-лейбл чи назва події — не вигадувати самостійно; це територія `cro-specialist`.
