# Beauty CRM — Доменна модель

**Current version:** 0.1 (2026-10-07)

## 1. Основні сутності

### Структурні одиниці (каталог)

- **Location** — заклад (салон, барбершоп). Містить часові пояси (`timezone` за IANA), адресу, контакти.
- **Specialist** — майстер (перукар, косметолог). Може працювати в кількох закладах.
- **SpecialistLocation** — зв'язок майстра з закладом + графік роботи (`working_hours` — JSON тиж. розклад).
- **Service** — послуга (стрижка, фарбування) з тривалістю в хвилинах.
- **ServicePrice** — ціна послуги. Може бути мережевою (LocationId NULL) або override закладу.

### Записи & клієнти

- **Appointment** — запис на послугу (візит клієнта до майстра в закладі у часовому проміжку).
  - **Статуси:** `pending` (новий) → `confirmed` (підтверджено) → `completed` (завершено) або `cancelled` / `no_show` (без явки).
  - **Період:** `starts_at` + `duration_minutes` → `ends_at` (обраховується тригером БД).
  - **Вартість:** `price_original` (без знижок), `price_final` (після акцій).
  - **Джерело:** `admin` (адмін закладу), `online` (веб), `telegram` / `instagram` (канали).
  - **Оплата:** `payment_method` (card / cash), `payment_status` у таблиці Payment.
  - **Скасування:** `cancelled_at`, лихва залежить від часу скасування vs. час візиту (TASK-685).
- **Client** — клієнт (повна інформація + contact). Мягка видалення (`deleted_at`).
- **ClientNote** — нотатка мастера до клієнта (автор, текст).
- **Payment** — платіж за запис (статус: pending / paid / failed; для оплат карткою).
- **Reminder** — нагадування (за певний час до запису).

### Акції

- **Promotion** — акція/знижка (%, фіксована сума) зі скидом на послуги/локації.
- **PromotionLocation**, **PromotionService** — розподіл акції по закладам/послугам.

### Канали & комунікація

- **Channel** — інтеграція з каналом (Telegram, Instagram тощо). Секрети зашифровані.
- **Conversation** — чат/тред між закладом й клієнтом у каналі.
- **Message** — повідомлення (в/вихід, статус: received / draft / pending / sent / failed).
- **AiAction** — дія AI (запропонована, підтверджена або відхилена), журнал для аудиту.

## 2. Статуси запису (Appointment.Status)

```
pending      → новий запис, потребує підтвердження (або автомат. confirmed для онлайн-оплати карткою)
confirmed    → підтверджено, буде надіслано нагадування
completed    → завершено (після часу starts_at + duration)
cancelled    → скасовано клієнтом чи адмін (повернення за політикою租用 TASK-685)
no_show      → записаний, але клієнт не прийшов
```

**Переходи:**
- `pending` ← нове створення
- `pending` → `confirmed` (адмін чи система при оплаті карткою, для cash=pending)
- `confirmed` → `completed` (після часу завершення)
- `confirmed`/`pending` → `cancelled` (на запит; перевірка скасування в межі часу)
- будь-хто → `no_show` (адмін, якщо клієнт не прийшов)

## 3. Напрямок повідомлень (Message.Direction, SenderType)

- **Inbound:** клієнт → платформа (webhook від каналу).
- **Outbound:** платформа → клієнт (AI-відповідь, нагадування, сповіщення).
- **SenderType:** `client`, `assistant` (AI), `specialist`, `system`.

## 4. AI-режими

Визначені в контрактах (TASK-677):
- **`suggest`** — AI пропонує дію, не виконує. Адмін переглядає й схвалює.
- **`confirm`** (за замовчуванням) — AI пропонує, потім виконує лише низькоризикові (find_slots, get_prices, draft_reply).
- **`auto`** — AI виконує все (потребує явної прив'язки per tenant).

## 5. Сегментація клієнтів для розсилок

- **Фільтри:** розташування(я), послуга(и), історія (колишні, активні), дата останнього візиту.
- **Обмеження:** лише зі **згодою** (`marketing_consent = true`), не відписані (`unsubscribed = false`).
- **Часовий контроль:** розсилки 09:00–20:00 локальні за закладом, максимальна знижка 20%.

## 6. Таймзони й локалізація часу

- Кожен **Location** має `timezone` (IANA: "Europe/Kyiv").
- **WorkingHours** — JSON per SpecialistLocation, локальний час для цього закладу.
- **Розрахунок слотів:** дата (DateOnly) + часовий пояс → UTC для порівняння з `starts_at`.
- **Запис:** `starts_at` завжди в UTC (DateTimeOffset).

## 7. Модулі функціоналу (на рівні tenant)

Контролюються `Tenant.modules` (массив), активуються [RequireModule] на ендпоінтах:

- `beauty_booking` — слоти, запис, отримання, скасування.
- `beauty_catalog` — послуги, ціни, акції, превью ціни.
- `beauty_clients` — картка клієнта, нотатки, історія.
- `beauty_analytics` — звіти й метрики.
- `beauty_channels` — налаштування каналів, вхідні webhook.
- `beauty_ai` — журнал AI-дій, підтвердження/відхилення.

**Поведінка:** якщо модуль вимкнений, ендпоінт повертає `403 module_disabled`; login/refresh теж -> `401`.

## 8. Ролі користувачів

- **`platform_operator`** — створення tenant (API-ключ `.env`, не користувач у БД).
- **`owner`** — власник tenant (один, не может бути видалено; керує адмін/спеціалістами).
- **`admin`** — адміністратор закладу; керує спеціалістами, каталогом, каналами, звітами.
- **`specialist`** — майстер; бачить/змінює лише власні записи, історію клієнтів.

**Матриця доступу:**
- Booking endpoints: усі ролі можуть читати; specialist — лише власні записи.
- Catalog: читання — усі; зміни — owner/admin.
- Clients/Analytics/Channels/AI: owner/admin.
- Platform API: только platform_operator (X-Platform-Key).

## 9. Ідемпотентність повідомлень

Щоб уникнути дублювання в webhook-переадресаціях:

- **IdempotencyKey** на `Message` — унікально per tenant, напр. `telegram:message_id:retry_1`.
- **Worker jobs** — ключ за типом подій (напр. `reminder:{appointmentId}:{offset}`).

## 10. Видалення даних

- **Soft delete:** `Client.deleted_at` (історія, але схована з UI).
- **Cascade:** дочірні рядки (ClientNote, Appointment, Message, Reminder) видаляються при видаленні батька.
- **Personal data:** клієнти зберігаються для історії, но з `deleted_at` позначені й виключені з аудиторій розсилок.
