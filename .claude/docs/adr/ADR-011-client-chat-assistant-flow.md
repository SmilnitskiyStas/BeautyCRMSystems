# ADR-011: Асистент у чаті клієнта — Telegram → ШІ → відповідь і запис на послугу

**Date:** 2026-10-24

**Status:** proposed. Потребує human gate (§8): семантика режимів для чату клієнта, SECURITY DEFINER-функція переліку tenants, юридичний пункт ADR-010 §7.3 (відкритий). До закриття §8.3 заборонено мердж у `main` і деплой у прод; реалізація у feature-гілці й локальний smoke з тестовим ботом і тестовим ключем дозволені.

**Author:** project-architect

**Deciders:** продуктові рішення (1) long polling локально / webhook на проді й (2) запис після явного «Так» клієнта без менеджера затвердив користувач 2026-10-24. Решту рішень цього ADR погоджують на gate.

**Уточнює ADR-004** (вхідний потік, outbox), **ADR-005** (поведінка режимів для чату клієнта, набір tools у scope клієнта) і **ADR-010** §2.8 (нейтральна автовідповідь при недоступному ШІ). Рішення цих ADR, яких тут не згадано, лишаються чинними.

Контракт: `.claude/docs/beauty-contracts.md` §21 (v0.24). Задачі: TASK-724…733 (TASK-723 уже зайнятий виправленнями за рев'ю TASK-719).

## 1. Контекст

Користувач підключив тестовий Anthropic-ключ (§20) і Telegram-бота й хоче поспілкуватися з ШІ-агентом бізнесу та записатися на послугу. Стан коду на 2026-10-24:

- **Вхід.** `WebhookIngestService` → `ChannelDirectory` (tenant за `channelId` через політику `channel_webhook_lookup`) → `InboundWebhookService` (підпис → `ParseInboundAsync` → `EfChannelMessageRepository.SaveInboundAsync` з ключем `{channel}:{channelId:N}:{chatId}:{messageId}`) → `IChannelQueue.EnqueueInboundAsync`. Реалізація черги `DeferredChannelQueue` **лише логує**. Повідомлення зберігається зі статусом `received`, і на цьому потік закінчується.
- **ШІ.** `BeautyAssistant` зареєстрований у DI, але **ніким не викликається**. Він однокроковий: бере лише поточний текст (`AssistantRequest.ClientMessage`), без історії розмови й без `conversationId`.
- **Telegram-парсер** бере лише `update.message.text`. Стікери, голос, фото, `edited_message` дають порожній результат, тож клієнт не отримує нічого. Тип чату (`private`/група) і `from.is_bot` не перевіряються. `update_id` не використовується. Long polling (`getUpdates`) немає.
- **Клієнт.** `beauty_conversations.client_id` ingest не заповнює. Таблиці зв'язку клієнт ↔ Telegram немає; у приватному чаті `chat.id` = `from.id`, тому розмова `(channel_id, external_chat_id)` (UNIQUE) однозначно ідентифікує користувача бота.
- **Tools у scope `Client`:** `find_free_slots`, `create_appointment`, `get_prices`, `get_active_promotions`, `get_client_context`, `draft_reply` (manager-only: `suggest_promotion`, `build_audience`). Для чату клієнта вони непридатні:
  - `create_appointment` у режимі `auto` створює запис **без** підтвердження клієнта;
  - `get_client_context` віддає нотатки персоналу й алергії, які клієнт може «витягнути» через injection;
  - `get_prices` віддає мережеву ціну без override закладу й без акції;
  - `CreateAppointmentAdapter` не має ідемпотентності, горизонту, сітки й лімітів, не маскує причини відмови, ставить `source=online` і вгадує заклад;
  - `DraftReplyAdapter` шукає розмову за `client_id`, якого в чаті немає.
- **Публічний запис** (`PublicBookingService.CreateAsync`) має потрібні правила (сітка 15 хв, `MaxDaysAhead`, ліміти, Idempotency-Key, маскування `specialist_unavailable|location_closed|outside_location_hours` → `slot_unavailable`), але вимагає ім'я й телефон, CAPTCHA й HTTP-контекст.
- **Відправка.** Outbox: `OutboundDispatcher` → `OutboxProcessor` (inline, 3 спроби) і Node-воркер `pollOutbox` (кожні 30 с, лише `pending`, реальний HTTP, `Channels:UseMocks` не знає). Inline-шлях `DraftReplyAdapter` захищений claim `draft → sending` (L7).
- **Перелік tenants для фонових задач.** Runtime-роль без BYPASSRLS не бачить рядків без `app.tenant_id`. Воркер бере tenants зі статичного `WORKER_TENANT_IDS`. `beauty_list_tenants()` (SECURITY DEFINER) лише запропоновано (TASK-686, відкрите питання).
- **Менеджерського inbox немає**: API розмов/повідомлень відсутній, handoff видно лише в `GET /ai/actions`.

## 2. Рішення

### 2.1 Вхід: один ingest, два транспорти
- **Ядро ingest** (`InboundIngestCore`, рефактор `InboundWebhookService`): `ResolvedChannel` + список `InboundMessage` → дедуплікація й збереження (наявний ключ `{channel}:{channelId:N}:{chatId}:{messageId}`) → сигнал черги розмов `(tenantId, conversationId)`. Webhook = перевірка підпису (без змін) + `ParseInboundAsync` + ядро. Polling = `getUpdates` + той самий `ParseInboundAsync` + ядро (підпис не потрібен: бот сам тягне оновлення з Telegram по TLS своїм токеном).
- **Дедуплікація** — за `chat_id:message_id`, однаково для обох транспортів, тож перемикання webhook ↔ polling і повторна видача `getUpdates` дублів не дають. `update_id` використовується лише як offset.
- **Long polling** — `TelegramPollingService` (`BackgroundService` у процесі API, .NET), а не Node-воркер: ingest, розшифрування секретів каналу, парсер і `BeautyAssistant` живуть у .NET.
  - Вмикається конфігом: `Channels:Telegram:Polling:Enabled=true` + явний список `Channels:Telegram:Polling:ChannelIds` (id каналів не секретні). Дозволено **лише в Development**; поза ним старт падає, як для `Channels:UseMocks`. Потрібно `Channels:UseMocks=false`, бо mock-парсер не розуміє формат Telegram (інакше теж помилка старту).
  - Канал резолвиться через наявний `ChannelDirectory.ResolveAsync` (tenant і токен з БД).
  - Цикл: `getUpdates?offset={last+1}&timeout=25&allowed_updates=["message"]` → ядро ingest → upsert offset у **БД** (`beauty_channel_poll_state`, RLS) **після** збереження пакета. Збій між збереженням і offset дає повторну видачу, яку з'їдає дедуплікація.
  - Lease рядка poll state гарантує одного споживача на бота.
  - Помилки: `409` (активний webhook) → лог `telegram_webhook_active` і backoff 60 с, webhook **не** видаляється автоматично; `401/404` → polling каналу зупиняється; `429` → `retry_after`; мережа → експоненційний backoff до 60 с. URL з токеном ніколи не логується, тому HTTP-клієнт без логування URI (не `IHttpClientFactory` з дефолтним logging).
- **На проді лишається webhook** (`X-Telegram-Bot-Api-Secret-Token`, без змін).
- **Парсер Telegram (розширення):**
  - лише `chat.type = "private"`; повідомлення від `from.is_bot=true` і з груп ігноруються;
  - `edited_message`, `callback_query` та інші типи оновлень у V1 ігноруються;
  - не-текст (стікер, голос, відео, фото, документ, контакт, локація) зберігається як `kind=unsupported` з плейсхолдером (`[voice]`, `[sticker]` …) без завантаження медіа й без телефону з контакту;
  - підпис фото (`caption`) іде як текст;
  - `/start`, `/help` дають `kind=command`.

### 2.2 Черга розмови й одночасність
- **Сигнал:** нова реалізація `IChannelQueue` (замість `DeferredChannelQueue`) кладе `(tenantId, conversationId)` у in-process канал, який читає `ConversationWorker` (hosted service). **Recovery-sweeper** кожні 30 с обходить tenants (§2.9) і бере розмови з `received`-повідомленнями старшими за 10 с або з простроченим lease. Сигнал у пам'яті лише прискорює обробку; джерело істини — БД.
- **Одна розмова — один виклик за раз:** lease на рядку `beauty_conversations` через умовний UPDATE (`ai_lease_until < now()` → `now()+120 с`, `ai_lease_owner`). Програвший нічого не робить. `pg_advisory_xact_lock` на час виклику LLM не тримається: це довгі транзакції при сесійному tenant context (§14.2 M4).
- **Пакет:** під lease беруться всі `received` вхідні повідомлення розмови за `(sent_at, external message id)` і обробляються **одним ходом** (одна відповідь на кілька швидких повідомлень). Повідомлення, що прийшли під час ходу, обробляються наступним ходом до звільнення lease.
- **Не відповідати двічі:** відповідь пишеться з `idempotency_key = ai-reply:{conversationId}:{lastInboundMessageId}` (UNIQUE `(tenant_id, idempotency_key)` вже є). Вхідні повідомлення ходу стають `processed` у **тій самій транзакції**, що й вставка відповіді. Повтор після падіння (lease прострочився) може повторити виклик LLM (зайві токени), але друга відповідь не з'явиться.
- **Відправка:** відповідь вставляється одразу зі статусом `sending` (власник — процесор), після коміту йде inline `OutboundDispatcher`; успіх → `sent`, тимчасова помилка → `pending` (повтор воркером), постійна → `failed`. Воркер бере лише `pending`, тож гонки «inline ↔ воркер» немає (патерн L7). Reaper повертає `sending` старше 5 хв у `pending`. Це at-least-once: при падінні між `sendMessage` і `sent` можливий дубль (Telegram не має ключа ідемпотентності), ризик прийнято.

### 2.3 Конвеєр ходу (порядок детермінований, у коді)
1. Глобальний вимикач `ChatAssistant:Enabled` і прапорець каналу `settings.assistant.enabled` (default `false`, opt-in на канал). Вимкнено → повідомлення `processed` (`assistant_disabled`), відповіді немає (як зараз).
2. Розмова в handoff і `ai_paused_until > now` → `processed`, ШІ мовчить.
3. Режим `suggest` → автоматичних повідомлень клієнту немає (§2.6).
4. `kind=command`: `/start` → шаблон привітання; інша команда → шаблон «напишіть текстом». `kind=unsupported` → шаблон «розумію лише текст» (не частіше разу на 10 хв на розмову). Без виклику LLM і без токенів.
5. **Підтвердження запису** (§2.5) — до LLM.
6. Ліміти розмови (§2.8). Перевищено → один шаблон на вікно, далі тиша.
7. `HandoffRules` (скарга, оплата, людина) → handoff (§2.7).
8. `BeautyAssistant` (scope `ClientChat`, історія, контекст розмови) → текст / handoff / `ai_unavailable`.
9. Вихідний guard: видалити UUID і теги-розділювачі, обрізати до 3500 символів, надсилати plain text без `parse_mode`. Якщо в цьому ході успішно спрацював `prepare_booking`, до тексту додається **канонічний підсумок, згенерований кодом** (не LLM).
10. Транзакція: вставка відповіді + `processed` + прив'язка підсумку до пропозиції (`summary_message_id`, статус `shown`) → коміт → inline-відправка.

### 2.4 Tools у scope `ClientChat` (новий scope; `Client`/`Manager` не змінюються)
| Tool | Стан | Що робить |
|---|---|---|
| `list_locations` | новий | активні заклади (`PublicBookingService.ListLocationsAsync`): id, назва, адреса, зона, години, вихідні |
| `list_services` | новий (замість `get_prices`) | послуги закладу з ціною override + акцією на зараз (`PublicBookingService.ListServicesAsync`) |
| `list_specialists` | новий | придатні майстри закладу (`ListSpecialistsAsync`), лише публічні поля |
| `find_slots` | новий (замість `find_free_slots`) | `PublicBookingService.GetSlotsAsync` (горизонт `MaxDaysAhead`), до 20 слотів, ISO + локальна мітка + зона |
| `get_active_promotions` | є | без змін |
| `prepare_booking` | новий | етап 1: перевіряє, що слот є серед `find_slots` на ту дату, рахує ціну, створює пропозицію; повертає моделі підсумок і «запис ще НЕ створено, попроси відповісти «Так»» |
| `request_handoff` | новий | модель просить передати менеджеру: `complaint\|unclear\|human_requested\|medical\|other` |

- **Виключено з `ClientChat`:** `create_appointment`, `get_client_context`, `draft_reply`, `suggest_promotion`, `build_audience`. Причини — §1. Виклик виключеного tool → `tool_not_allowed_in_client_scope`.
- **Етап 2 (`confirm_booking`) — не tool моделі.** Його виконує конвеєр (§2.5) за детермінованою перевіркою відповіді клієнта. Модель не може «підтвердити» запис ні словами, ні викликом.
- Схеми без `tenantId`/`clientId`/`conversationId`: ці значення лише з `AiToolContext`. Зайві поля ігноруються. id від моделі шукаються під RLS (чужий = not found). Якщо канал має `location_id`, він стає закладом за замовчуванням; якщо в tenant один активний заклад — він.

### 2.5 Запис: двоетапне підтвердження, перевірне в коді
- **Пропозиція** (`beauty_chat_booking_proposals`): conversation, location, specialist, service, `starts_at`, тривалість, `price_original/price_final/promotion_id`, `expires_at` (`ChatAssistant:ProposalTtlMinutes`, 15), статус `prepared → shown → confirmed|rejected|expired|superseded|failed`, `confirmation_token_hash` (SHA-256 від 128-бітного випадкового токена; токен не передається ні моделі, ні клієнту), `summary_message_id`, `appointment_id`. На розмову одна активна (`prepared|shown`), новий `prepare_booking` замінює попередню.
- **Етап 2 у конвеєрі.** Запис створюється **лише** якщо всі умови виконано:
  - (а) у розмови є пропозиція `shown`;
  - (б) поточний хід складається рівно з **одного** вхідного повідомлення, і воно **перше** після `summary_message_id`;
  - (в) його нормалізований текст (lowercase, trim, без пунктуації/емодзі) ∈ `{так, так підтверджую, підтверджую, yes, да}`;
  - (г) `now < expires_at`;
  - (д) пропозиція належить цій розмові.
  
  Тоді виконується `ChatBookingService.ConfirmAsync(proposalId)`. Негатив (`ні`, `нет`, `no`, `скасувати`) → `rejected` + шаблон. Будь-що інше → `superseded`, далі звичайний хід LLM; щоб записатися, потрібна нова пропозиція і нове «Так».
- **`ChatBookingService`** (Application) — той самий шлях і правила, що й публічний запис. Зі `PublicBookingService` виноситься спільне ядро `OnlineBookingCore` (поведінка публічного API не змінюється, наявні тести проходять без змін):
  - сітка 15 хв, `MaxDaysAhead`, перевірки `BookingService.CreateAsync` (`slot_in_past → location_closed → specialist_unavailable → outside_location_hours → outside_working_hours → slot_unavailable`, години закладу §18, вихідні §17, відсутності §13, advisory/FOR SHARE-блокування);
  - маскування причин як у публічному API (`slot_unavailable`);
  - ідемпотентність: `idempotency_key_hash = SHA-256("chat:" + proposalId)` + відбиток тіла, із циклом replay, як у публічному запису;
  - ліміти `MaxActiveBookingsPerPhone` (3) і `MaxCreatesPerPhonePerHour` (5) застосовуються **на клієнта** (записи `source ∈ {telegram, instagram}`).
  
  Відмінності від публічного запису: без CAPTCHA, honeypot, імені й телефону (клієнт уже ідентифікований розмовою); `source=telegram`; `paymentMethod=cash` (оплати в чаті немає, `IPaymentService` без провайдера), тож статус `confirmed` за правилом публічного запису для готівки; `reminder=none`.
- **Ціна:** `BookingService.CreateAsync` отримує адитивний `ExpectedPriceFinal`. Якщо quote на момент запису відрізняється від пропозиції → `409 price_changed`, запис не створюється, клієнту пропонується новий підсумок.
- **Клієнт** створюється **ліниво при етапі 2**, а не на першому повідомленні: так спам-розмови не засмічують CRM. `full_name` = ім'я з профілю Telegram (2–100 символів; fallback «Клієнт Telegram»), `phone=NULL`, `marketing_consent=false`; `beauty_conversations.client_id` заповнюється. Телефон не запитується. Відома межа: людина, яка вже записувалась онлайн за телефоном, стане окремим клієнтом (злиття клієнтів немає).
- **Відповіді клієнту** — шаблони коду: підтвердження (послуга, майстер, заклад з адресою, дата/час у зоні закладу, ціна, «скасувати/змінити — напишіть сюди, адміністратор допоможе»); `slot_unavailable` → вибачення + LLM пропонує інші слоти наступним ходом; `expired`, `price_changed`, `booking_limit_reached`. Повторне «Так» після `confirmed` нового запису не створює.

### 2.6 Режими для чату клієнта (уточнення ADR-005)
| Режим | Інформаційні відповіді клієнту | Запис |
|---|---|---|
| `suggest` | не надсилаються: відповідь зберігається як чернетка (`draft`) з `conversationId`, менеджер надсилає (approve) | `prepare_booking` лише `drafted`, підсумок клієнту не показується; шляху «Так» немає |
| `confirm` (default) | надсилаються автоматично | лише після явного «Так» клієнта (§2.5), менеджер не потрібен |
| `auto` | надсилаються автоматично | так само лише після «Так». `auto` **не** скасовує підтвердження клієнта |

**Правило:** у чаті клієнта підтвердження запису = підтвердження **клієнта**, власника запису, і в `confirm`, і в `auto`. Без перевіреного кодом «Так» запису немає в жодному режимі.

Чому так:
1. Публічна форма вже дозволяє анонімному клієнту записатися без менеджера. Запис у чаті з тими самими правилами й канонічним підсумком еквівалентний натисканню «Записатися», тож додаткового ризику немає.
2. Підтвердження менеджером зробило б чат повільнішим за форму без виграшу в безпеці.
3. `auto` не може пропустити «Так», бо параметри запису обирає LLM, і клієнт має побачити й прийняти підсумок.

Інформаційні відповіді в `confirm` надсилаються автоматично, бо вони спираються лише на read-only tools (ADR-005: читання в `confirm` виконується одразу). Ціни, слоти й підсумок формує код. Це змінює рядок `draft_reply` таблиці ADR-005 **лише для каналу чату клієнта**, тож потребує gate (§8.1).

### 2.7 Handoff менеджеру
- **Тригери:** `HandoffRules` (скарга, оплата, людина); `request_handoff` від моделі; `ai_unavailable` (немає ключа, квота, частота, збій провайдера — `BeautyAssistant` уже повертає `HandedOff`); повторні помилки tools (≥ 3 у ході); прохання скасувати чи перенести запис (у V1 tools для цього немає).
- **Дія:** розмова `ai_state=handoff`, `handoff_reason`, `ai_paused_until = now + ChatAssistant:HandoffPauseHours` (12); журнал `handoff`. Клієнт отримує **один** нейтральний шаблон без LLM («Передаю ваше питання адміністратору, вам відповідять найближчим часом»). Це уточнення ADR-010 §2.8, де було «без автовідповіді». Поки пауза діє, ШІ мовчить. Після паузи або `resume-ai` менеджером ШІ повертається.
- **Менеджер** бачить handoff у `GET /ai/actions` (є) і в мінімальному inbox (TASK-729/730: список розмов, що потребують уваги, повідомлення, відповідь через outbox, `resume-ai`). Сповіщень (email/push) у системі немає, тож вони поза цим ADR.

### 2.8 Захист від injection, ліміти, мова
- Повідомлення клієнта йдуть лише як `user` у `<client_message>` (`PromptInjectionGuard.Prepare` → `Wrap` з TASK-723: нормалізація, ≤ 2000 кодових точок, знешкодження подоб тегів; обрізання позначається). Результати tools — `WrapToolResult` (`<tool_result_data>`). Відповіді асистента в історії йдуть як `assistant`. Історія: останні 20 повідомлень, не більше 6000 символів. Результати tools попередніх ходів не відтворюються: стан запису лежить у БД (пропозиція).
- Службові «команди» в тексті (`system:`, `mode=auto`, `/admin`, «ігноруй інструкції») — це дані. Режим, scope, tenant і підтвердження перевіряє код. `IsSuspicious` → журнал `injection_suspected`.
- Клієнт не може записатися на чужий слот, оформити запис на чужого клієнта чи скасувати чужі записи. Клієнт береться лише з розмови; tools скасування й чужих записів у scope немає; пропозиція прив'язана до розмови; слот перевіряється кодом.
- Ліміти: `MaxCallsPerConversationPerMinute` (6) і `PerDay` (100) — ходи LLM на розмову; tenant-ліміти ADR-010 (`PerTenantPerMinute`, місячні) без змін; `MaxToolIterations` (6); вхід > 4096 символів неможливий у Telegram, LLM бачить ≤ 2000.
- **Мова:** правило ядра «Відповідай українською» змінюється на «Відповідай мовою клієнта; якщо мову не визначено — українською». Це зміна ядра `PromptComposer`, ADR-010 §2.6 допускає її через ADR. Шаблони коду в V1 лише українською; англійські — V2.
- Ядро доповнюється: «не обіцяй знижок, цін і слотів, яких немає в результатах tools; запис створює система лише після «Так» клієнта на показаний підсумок; не кажи, що запис створено, доки система цього не підтвердила». Заборони розкривати промпт, ключі й дані інших компаній уже є в ядрі (ADR-010).
- Облік: кожна ітерація LLM — запит `role=chat` у `beauty_ai_usage` (`TenantAiClient`, без змін). Детерміновані шаблони токенів не витрачають.

### 2.9 Перелік tenants для sweeper
Нова SECURITY DEFINER-функція `beauty_list_tenants()` повертає лише `tenant_id` активних tenants. EXECUTE мають runtime-ролі API й воркера, вона закриває й відкрите питання TASK-686. Далі вся робота йде під `app.tenant_id` (RLS FORCE). Це розширення меж RLS (вузьке, без даних), тому потрібні gate (§8.2) і security review. Без функції sweeper обходить лише tenants каналів зі списку polling. Тоді webhook-канали на проді відновлюються тільки при наступному повідомленні розмови, і це неприйнятно для прод-готовності.

## 3. Модель загроз (стисло)
| Загроза | Захист |
|---|---|
| Injection «створи запис без підтвердження / режим auto» | етап 2 не є tool, «Так» перевіряє код (§2.5), режим і scope в коді |
| LLM каже «записано», хоча запису немає | правило ядра + підсумок і підтвердження з шаблонів коду; текст LLM не є джерелом факту запису |
| Витяг нотаток персоналу / алергій | `get_client_context` поза `ClientChat` |
| Чужий tenant / клієнт / слот | tenant з каналу, клієнт з розмови, RLS, слот перевіряється кодом, `TenantMismatchException` |
| Подвійна відповідь / подвійний запис | lease, ідемпотентний ключ відповіді, ідемпотентність запису за пропозицією, CAS статусу пропозиції |
| Флуд і перевитрата | пакетування ходу, ліміти на розмову й tenant, шаблони без LLM для медіа й команд |
| Витік токена бота (URL `bot{token}`) | URL не логується, помилки без URL (як у `HttpSend`), токен лише в зашифрованих credentials |
| Запис клієнтом без контакту | ліміти на клієнта, лінивий клієнт; ризик no-show прийнято як для публічного запису (менеджер скасовує) |

## 4. Наслідки
Позитивні:
- Реальний потік «повідомлення → відповідь → запис» на чинних правилах запису, без нового шляху створення записів.
- Підтвердження перевірне в коді й не залежить від слів моделі.
- Однакова дедуплікація для webhook і polling; локальний smoke без публічного HTTPS.

Негативні / прийняті компроміси:
- Новий фоновий процес в API (полінг, воркер розмов, sweeper). Polling — лише один інстанс і лише Development.
- At-least-once відправка (рідкісний дубль при падінні між `sendMessage` і `sent`).
- Повтор ходу після падіння може витратити токени двічі.
- Клієнти з чату без телефону: можливі дублікати з клієнтами онлайн-запису.
- Строга граматика «Так»: «так, оплачу на місці» — не підтвердження (безпечно, але менш зручно).
- `HandoffRules` («оплат») дає хибні handoff у розмові про оплату. Прийнято до уточнення правил.
- Шаблони лише українською у V1.

## 5. Розглянуті альтернативи
- **Polling у Node-воркері** — відхилено: дублювання парсера, ingest і секретів; `BeautyAssistant` у .NET, а виклик API з воркера — нова внутрішня поверхня автентифікації.
- **Режим polling прапорцем у `beauty_channels.settings`** — відхилено: потрібен міжtenant-ний перелік каналів (розширення RLS), admin міг би ввімкнути polling на проді з кількома інстансами (Telegram `409`). Polling — питання деплою, тому він у конфігу.
- **Локально webhook через тунель (ngrok тощо)** — не заборонено, але це не рішення продукту; коду не потребує.
- **`confirm_booking` як tool моделі з `confirmation_token`** — відхилено: код однаково мусить перевірити «Так». Окремий tool — це зайва поверхня injection і токени, а модель могла б викликати його на неоднозначній відповіді. Токен лишається серверним ідентифікатором пропозиції й ключем ідемпотентності.
- **Підтвердження менеджером запису з чату в `confirm` (буквально ADR-005)** — відхилено рішенням продукту (2): повільніше за публічну форму без виграшу в безпеці.
- **`auto` створює запис без «Так»** — відхилено: параметри обирає LLM.
- **`PublicBookingService.CreateAsync` напряму** — відхилено: вимагає телефон (зайві ПД), CAPTCHA, IP-ліміти. Спільне ядро зберігає однакові правила.
- **`CreateAppointmentAdapter` / `create_appointment`** — відхилено: немає ідемпотентності, горизонту, лімітів і маскування, `source=online`, вгадування закладу.
- **Лише in-memory черга** — відхилено: кілька інстансів і відновлення після падіння.
- **BullMQ/Redis** — відкладено: рішення про продюсер Redis не ухвалено (`DeferredChannelQueue`).
- **Advisory lock на час виклику LLM** — відхилено: довгі транзакції при сесійному tenant context.
- **Клієнт на першому повідомленні / запит телефону** — відхилено: засмічення CRM і зайві ПД.
- **«Без автовідповіді» при недоступному ШІ (ADR-010 §2.8)** — уточнено: один нейтральний шаблон, бо інакше клієнт не знає, що його почули.
- **Inline-кнопки Telegram «Так/Ні» (callback_query)** — відкладено на V2: потрібні `reply_markup` в `OutboundMessage` і парсер callback. Текстове «Так» достатнє й перевірне.

## 7. Поетапність
- **V1:** §2.1–§2.9, Telegram (webhook + polling у Development), scope `ClientChat`, двоетапний запис, handoff + мінімальний inbox, шаблони українською.
- **V2:** Instagram через той самий конвеєр (вікно 24 год → handoff), inline-кнопки «Так/Ні», шаблони англійською, перегляд і скасування власних записів клієнтом у чаті (tools, прив'язані до `ctx.ClientId`), нагадування для записів із чату, злиття клієнтів.

## 8. Human gate
1. **Семантика режимів у чаті клієнта (§2.6)**: автоматичні інформаційні відповіді в `confirm`; «Так» клієнта достатнє для запису в `confirm` і `auto`; `suggest` нічого не надсилає. Потрібне підтвердження продукту.
2. **`beauty_list_tenants()` SECURITY DEFINER** (межа RLS/авторизації, `workflow/human-gates.md`). Потрібне погодження + security review (TASK-732).
3. **Юридичне (ADR-010 §7.3) — ВІДКРИТО.** Тексти розмов клієнтів ідуть провайдеру ШІ. До закриття заборонено мердж у `main` і деплой у прод; `ChatAssistant:Enabled=false` за замовчуванням. Дозволено: feature-гілка, тести, локальний smoke з тестовим ботом і тестовим ключем.

## 9. Scope of truth
ADR-011 авторитетний для: потоку «вхідне повідомлення каналу → черга розмови → асистент → відповідь»; транспорту Telegram (webhook на проді, long polling лише в Development, offset у БД); одночасності й ідемпотентності обробки розмови; набору tools scope `ClientChat`; двоетапного запису з чату й правила підтвердження клієнтом; поведінки режимів `suggest|confirm|auto` у чаті клієнта; handoff із чату; ідентифікації клієнта каналу. Зміна будь-чого з цього (tool створення запису для моделі, запис без «Так», polling на проді, новий шлях створення записів, запит ПД у чаті) потребує нового ADR. Поля, коди й конфіг — контракт §21.
