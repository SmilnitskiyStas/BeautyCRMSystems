## 1. Context

### 1.1 Стан коду (2026-11-18, перевірено)

- Складу, товарів і залишків у системі немає. ADR-010 §2.11 (рядок 145) прямо фіксує: «Облік товарів — окрема функція з власною специфікацією й ADR». Цей ADR і є такою функцією.
- Собівартість послуги (ADR-014) — фіксована сума на послугу (мережа + override закладу) зі знімком на записі в момент `completed` (`EfBeautyStore.Booking.cs`, `CompleteWithCostSnapshotAsync`: один умовний `UPDATE … WHERE status IN ('pending','confirmed')`). Списання матеріалів немає.
- Модулі tenant: `BeautyModules.All` (вмикаються за замовчуванням) і `BeautyModules.Known` (`All` + опційні). Прецедент опційного модуля — `beauty_marketing`: у `Known`, не в `All`, без backfill (`AuthModels.cs`).
- Права (ADR-023): каталог у коді (`PermissionCatalog`, `Version = 1`, 18 ключів), пресети (`PermissionPresets`), матеріалізовані рядки `user_permissions`, перевірка `[RequireModule]` (−3100) → `[RequirePermission]` (−3000), `own` через `users.specialist_id`. Новий ключ — лише з міграцією backfill і збільшенням `Version`.
- Помилки: `Result<T>` / `Error` (`Validation` → 422, `NotFound` → 404, `Conflict` → 409, `Forbidden` → 403, `TooManyRequests` → 429), `Error.ForbiddenPermission(permission, required)`.
- Схема: `Base`/`TenantFk` у `BeautyDbContext.cs` (композитні FK `(tenant_id, x_id)`), RLS `ENABLE`+`FORCE`+`tenant_isolation`, CHECK-и як текст. Append-only для app-ролі робиться `REVOKE UPDATE, DELETE` (прецеденти `beauty_marketing_consent_events`, `user_access_audit`). GRANT-и живуть не в міграції, а синхронно в `scripts/dev/setup-db.ps1` і `deploy/staging/db/grants.sql` (перевіряє `worker/src/staging-grants-sync.test.ts`). Після міграції перегенеровується `worker/src/testing/schema.sql` (без BOM, LF; `schema-drift.test.ts`).
- Ідемпотентність POST уже має патерн (§3 контракту, публічний запис): заголовок `Idempotency-Key`, SHA-256 ключа й тіла, `Idempotent-Replayed: true`, `422 idempotency_key_reused`.
- Заклади не видаляються, лише деактивуються (`LocationService`, `IsActive`).
- Сповіщень персоналу (окрім inbox і бейджа `InboxBadge`) немає. Telegram-зв'язки є лише в клієнтів.

## 2. Decision

### 2.1 Модуль

- `BeautyModules.Inventory = "beauty_inventory"`: додається в `BeautyModules.Known`, **не** в `All`. Нікому не вмикається за замовчуванням, backfill модулів немає. Вмикається явно: control plane (`PATCH` tenant, ADR-018 / §27), platform-скрипти, dev-скрипт `scripts/dev/enable-inventory.ps1` (аналог `enable-marketing.ps1`); `create-salon.ps1`, `seed.ps1`, `deploy/staging/create-tenant.sh` отримують опцію модуля.
- Парна правка в ShelfGuard (`setModules`, зовнішній репозиторій) — окрема задача поза цим репо.
- Усі ендпоінти складу мають `[RequireModule("beauty_inventory")]` (перший за порядком фільтрів, `403 module_disabled`).
- Вимкнення модуля не видаляє даних: після повторного ввімкнення залишки, партії й журнал на місці (як права за ADR-023 §2.7). Автосписання (етап 2) і воркер сповіщень для tenant з вимкненим модулем не працюють.

### 2.2 Права (блок `inventory`, ADR-023)

Каталог отримує блок `inventory` (маршрут меню `/beauty/inventory`), `PermissionCatalog.Version = 2`:

| Ключ | Рівні (зростання) | Модуль | Обмеження | Що відкриває |
|---|---|---|---|---|
| `inventory.view` | `none` · `own` · `all` | `beauty_inventory` | — | каталог товарів, залишки, партії, рух, інвентаризації (лише перегляд) |
| `inventory.manage` | `none` · `own` · `all` | `beauty_inventory` | `lte inventory.view` | надходження, списання, переміщення, інвентаризація, налаштування товару по закладу; `all` — ще й каталог товарів і постачальники |
| `inventory.costs` | `none` · `view` · `edit` | `beauty_inventory` | `requires revenue.view = all` | закупівельні ціни (товар, партія, рух), вартість залишків; `edit` — задавати їх |
| `inventory.sales` (етап 3) | `none` · `own` · `all` | `beauty_inventory` | `lte inventory.view` | продаж товарів клієнтам |

- **`own`** = заклади, де працює прив'язаний профіль майстра актора (`beauty_specialist_locations` для `users.specialist_id`, профіль активний). Без прив'язки або з неактивним профілем — порожня множина закладів (як `EffectiveSpecialistId → Guid.Empty`). Каталог товарів не прив'язаний до закладу, тому `inventory.view = own` бачить увесь каталог, але залишки, партії, рух та інвентаризації лише своїх закладів. Заклад поза scope дає `404 location_not_found` без розкриття існування.
- **Каталог товарів і постачальників** (створення й зміна) потребує `inventory.manage = all`, бо це дані мережі.
- **`inventory.costs`** вимагає `revenue.view = all`, як `revenue.costs`: закупівельні ціни — комерційна таємниця того ж класу, що собівартість ADR-014. Наслідок: без модуля `beauty_analytics` (`revenue.view` стає `none`) ціни складу не бачить ніхто, крім owner. Без права поле **відсутнє** в JSON (ADR-023 §2.9), а не `0`.
- **`inventory.sales`** визначено цим ADR, але в каталог він потрапляє **лише в етапі 3** (`catalogVersion 3`, окремий backfill). Причина: ключ без ендпоінтів нічого не означає, а UI показував би перемикач без дії (ADR-023 §4: «ключ без коду нічого не означає»).

**Пресети** (owner неявно має максимум):

| Ключ | owner | admin | deputy | specialist |
|---|---|---|---|---|
| `inventory.view` | all | all | all | own |
| `inventory.manage` | all | all | all | none |
| `inventory.costs` | edit | edit | none | none |
| `inventory.sales` (етап 3) | all | all | all | none |

**Backfill** (окрема міграція в TASK-877, ідемпотентна, одна транзакція, `ON CONFLICT DO NOTHING`):
- для кожного наявного `admin`, `deputy`, `specialist` записати рядки пресету; для `owner` — нічого;
- `inventory.costs` записується значенням пресету **лише якщо** поточний `revenue.view` користувача = `all`, інакше `none`. Без цього кастомізований admin (без виторгу) отримав би несумісний набір, і наступне збереження його доступів упало б з `422 permission_inconsistent`;
- `invites.permissions` (знімки запрошень, ADR-023 B1): доповнити відсутні ключі значеннями пресету ролі з тим самим правилом для `inventory.costs`; при прийнятті знімок однаково обрізається поточною стелею запрошувача;
- `users.access_version + 1` для користувачів, яким додано рядки; аудит `migrated` (`actor_user_id = NULL`), як у ADR-023 §2.11;
- `Down` видаляє лише ключі `inventory.*`, якщо вони дорівнюють значенням backfill; якщо їх змінено вручну — відмова з явною помилкою (human gate).

Frontend дзеркалить ключі (`access.ts`, `permissions.ts`: пункт «Склад» у групі `catalog` `NAV_GROUPS`, `canOpen` за `inventory.view ≥ own` і модулем). Гарантію дає backend.

### 2.3 Модель даних (етап 1; точні колонки — контракт §32.3)

- **Тип товару:** `purpose` = `sale | salon_use | both` (текст + CHECK, конвенція `BeautyEnums.cs`). Відповідає вимозі «що на продаж, що для салону». У етапі 1 `purpose` лише класифікує й фільтрує; у етапі 2 норми матеріалів дозволені для `salon_use|both`, у етапі 3 продаж — для `sale|both`.
- **Одиниці:** довідник-перелік `pcs | ml | g | l | kg | pack` (шт, мл, г, л, кг, уп) як текст + CHECK. Для `pcs` і `pack` кількість — ціле число (Q4). Одиницю не можна змінити після першого руху (`422 unit_locked`).
- **Типи чисел:** кількості `numeric(14,3)`, гроші `numeric(12,2)`. На API — JSON number, ≤ 3 і ≤ 2 знаків після коми відповідно; більше знаків — 422, а не округлення.
- **Таблиці:** `beauty_suppliers`, `beauty_products` (штрихкод унікальний у межах tenant), `beauty_product_location_settings` (перевизначення мінімального залишку й дозволу товару в закладі), `beauty_stock_batches` (партії), `beauty_stock_levels` (агрегований рівень заклад×товар), `beauty_stock_operations` (заголовок операції: надходження, списання, переміщення, інвентаризація; ключ ідемпотентності), `beauty_stock_movements` (журнал рухів), `beauty_stocktakes` + `beauty_stocktake_lines`.
- **Мультитенантність:** усі таблиці через `Base`/`TenantFk` (композитні FK `(tenant_id, x_id)`), RLS `ENABLE`+`FORCE`+`tenant_isolation` (USING + WITH CHECK), `DO`-блок перевірки FORCE (зразок — міграція `20261026091203_beauty_service_costs.cs`). FK на заклади, товари, партії й користувачів з журналу — `RESTRICT` (історія не зникає каскадом).
- `beauty_stock_operations` відповідає «`transfer_id`» з плану: переміщення — це операція `kind = transfer`, і обидві його ноги посилаються на її `id` (`operation_id`). Окремої таблиці переміщень немає.

### 2.4 Облік: журнал, партії, рівні

1. **Журнал рухів append-only.** `beauty_stock_movements` і `beauty_stock_operations`: app-роль має лише `SELECT, INSERT` (`REVOKE UPDATE, DELETE` у `setup-db.ps1` і `grants.sql`). Виправлення робиться **новим** рухом (списання з причиною `correction` або інвентаризація), а не редагуванням. Типи рухів (CHECK одразу на всі етапи, щоб не змінювати обмеження append-only таблиці пізніше): `receipt`, `write_off`, `transfer_out`, `transfer_in`, `stocktake_adjust`, `service_consumption` (етап 2), `sale` (етап 3). Кількість знакова, знак узгоджений з типом (CHECK).
2. **Залишок = сума поточних кількостей партій.** `beauty_stock_batches.quantity ≥ 0` (CHECK). Для швидких запитів є `beauty_stock_levels (tenant_id, location_id, product_id, quantity)`, яку оновлює **та сама транзакція**, що й партії та журнал. Інваріанти (перевіряють тести): `level.quantity = Σ batches.quantity = Σ movements.quantity` для кожної пари заклад×товар.
3. **Серіалізація.** Будь-яка зміна залишку пари заклад×товар спершу бере `SELECT … FOR UPDATE` рядка `beauty_stock_levels` (створюючи його `INSERT … ON CONFLICT DO NOTHING`). Партії змінюються лише під цим блокуванням. Багаторядкові операції й переміщення блокують рядки в детермінованому порядку `(location_id, product_id)` за зростанням, щоб уникнути дедлоків.
4. **FEFO.** Списання з партій — «перший закінчується, перший виходить»: `expires_on ASC NULLS LAST, received_at ASC, id ASC`, лише партії з `quantity > 0`. Прострочена партія — `expires_on <` локальної дати закладу (за `timezone` закладу і `TimeProvider`). Ручне списання бере FEFO **з** простроченими (вони йдуть першими); переміщення бере FEFO **без** прострочених (Q7); автосписання (етап 2) і продаж (етап 3) прострочених не беруть ніколи. Клієнт може явно вказати партію рядка (`batchId`).
5. **Від'ємний залишок у етапі 1 заборонено:** ручне списання, переміщення й інвентаризація не можуть зробити партію чи рівень від'ємними (`422 insufficient_stock` з доступною кількістю). Єдиний виняток з'являється в етапі 2 (`service_consumption` при нестачі, §2.7).
6. **Переміщення** = одна операція `transfer`, у **одній транзакції**: `transfer_out` (від'ємні рухи з партій джерела за FEFO) і `transfer_in` (нові партії в закладі призначення з тим самим `expires_on`, `unit_cost`, `lot_number`, `received_at` і посиланням `source_batch_id`). Сума ніг дорівнює нулю. Стану «в дорозі» немає (Q5).
7. **Інвентаризація:** чернетка по закладу (одна відкрита на заклад), підрахунок по товарах; під час проведення різниця `counted − поточний рівень` (під `FOR UPDATE`) стає рухами `stocktake_adjust`: нестача списується за FEFO з простроченими, надлишок створює нову партію. Рух у закладі під час чернетки не блокується (Q8). Проведена інвентаризація незмінна.
8. **Закупівельна ціна** фіксується знімком на партії (`unit_cost`) у момент надходження: з рядка надходження (потрібне `inventory.costs = edit`) або з поточної ціни товару. Рух несе знімок ціни своєї партії. Зміна ціни товару не переписує партій.
9. **Ідемпотентність операцій:** кожен `POST` операції вимагає `Idempotency-Key`; ключ і тіло зберігаються як SHA-256 на `beauty_stock_operations` (унікальний частковий індекс у tenant). Повтор того самого ключа й тіла → `200` з тим самим результатом і `Idempotent-Replayed: true`; інше тіло → `422 idempotency_key_reused`.
10. **Час:** усі «зараз» і «сьогодні» беруться з `TimeProvider` і `timezone` закладу; тести не залежать від реального годинника.

### 2.6 Чого етап 1 не робить

Автосписання, норми матеріалів, сповіщення, воркер, Telegram, продаж, виручка від товарів, ПРРО — етапи 2–3. ШІ-асистент і ШІ-радник не отримують tools складу в жодному з етапів цього ADR (потрібне окреме рішення за ADR-005/ADR-010).

### 2.7 Етап 2 — автосписання на послузі й сповіщення (орієнтовно; контракт окремою версією §32)

- **Норми матеріалів:** `beauty_service_materials (service_id, product_id, location_id NULL = мережа, quantity)` за моделлю `beauty_service_costs`: мережа + override закладу; override діє на весь набір норм послуги в закладі. Лише товари `salon_use|both`. Задаються лише там, де салон вказав витрату.
- **Автосписання** у `CompleteWithCostSnapshotAsync` (`EfBeautyStore.Booking.cs`) у **тій самій транзакції**: після умовного `UPDATE` статусу, до `CommitAsync`. Ідемпотентно за `appointment_id` (унікальність `service_consumption` на запис і товар); якщо умовний `UPDATE` повернув 0 рядків (подвійне `completed`), списання не відбувається. Лише якщо модуль `beauty_inventory` увімкнено (аналог `MarketingModuleGate`). Знімок норм фіксується на візиті.
- **Нестача:** візит **завершується завжди** (рішення людини). Наявна кількість списується FEFO з непрострочених партій; непокрита частина записується рухом `service_consumption` без партії з позначкою нестачі, а залишок пари заклад×товар стає від'ємним через дефіцит на рівні (`beauty_stock_levels`), **партії від'ємними не стають**. Наступне надходження спершу погашає дефіцит. Точна механіка погашення (колонка дефіциту, зв'язок з рухом нестачі) — контракт етапу 2. Створюється сповіщення `shortage`.
- **Фіксована собівартість ADR-014 не змінюється.** Знімок `cost_snapshot` лишається фіксованою сумою. Перехід на собівартість із матеріалів — відкрите питання (Q11), за замовчуванням «ні».
- **Сповіщення персоналу:** нова таблиця `beauty_staff_alerts` (`kind: low_stock | expiring | shortage`, заклад, товар/партія, `dedupe_key` унікальний у tenant, статус `open|read|resolved`). Бейдж у меню за зразком `InboxBadge` (опитування 30 с), екран сповіщень. Видимість — за `inventory.view` і scope закладу.
- **Воркер:** `pollInventory` у `worker/src/scheduler/pollers.ts` через `forEachTenant`, реєстрація в `main.ts` як `beauty.inventory-alerts` раз на годину; «раз на добу» гейтиться локальним часом закладу. Гейт модуля (як `isMarketingEnabled`) і прапор `WORKER_INVENTORY_ENABLED` (`PollContext`, `.env.worker.example`). Ключі дедуплікації `lowstock:{loc}:{product}:{date}`, `expiry:{batch}:{bucket}`; пороги терміну 30/14/7 днів за замовчуванням, налаштовувані. Ролі воркера додаються мінімальні GRANT-и (SELECT на рівні/партії/товари/налаштування, INSERT/UPDATE на `beauty_staff_alerts`, INSERT в outbox) — синхронно в обох файлах GRANT.
- **Telegram власнику** — окрема підзадача етапу з окремим gate приватності (§2.9).

### 2.8 Етап 3 — продаж клієнтам, виручка, ПРРО/РРО (орієнтовно)

- `beauty_product_sales` + рядки (товар, кількість, ціна продажу, заклад, клієнт опційно, спосіб оплати, касир, час). Продаж списує партії FEFO тим самим механізмом (§2.4), прострочені не продаються, від'ємний залишок заборонено. Ціна продажу — мережева + override закладу (модель `beauty_service_prices`). Ключ `inventory.sales` додається в каталог разом з етапом (§2.2).
- **Виручка:** окремі **необов'язкові** поля `productRevenue` / `productCost` поряд із `revenue` в аналітиці (`EfBeautyStore.ClientsAnalytics.cs` `DailyAsync`, `AnalyticsService.cs`, frontend `types.ts`, `analytics/*`, mock). Семантика «записів», `revenue` і чистого доходу ADR-014 **не змінюється**. `productCost` — лише за `revenue.costs ≥ view` і `inventory.costs ≥ view`.
- **ПРРО/РРО:** порт `IFiscalService` без прив'язки до провайдера (патерн `IPaymentService`, рішення gate A3) + mock-адаптер. Вибір провайдера й фіскальні вимоги — **human gate** (§8). До його закриття продаж лише в dev/mock: модуль або прапор продажу вимкнено за замовчуванням поза dev (прецедент ADR-010 §7.3, ADR-015). Вибір провайдера оформлюється окремим ADR.

### 2.9 Telegram-сповіщення власнику: прив'язка й приватність (етап 2)

- Зараз Telegram-зв'язки є лише в клієнтів. Потрібна нова **прив'язка чату співробітника** (спершу лише owner; розширення на інші ролі — окреме рішення): deep-link з адмінки з одноразовим токеном (хеш у БД, TTL ≤ 15 хв, одне використання, патерн `setup-review-token-flow`), підтвердження в боті, збереження `chat_id` на користувачі в окремій tenant-таблиці під RLS FORCE.
- Повідомлення власнику **не містять ПД клієнтів**: лише заклад, товар, кількість, термін, тип сповіщення й посилання в адмінку. Відправка — через наявний outbox і `HttpChannelSender` (ADR-003).
- Вхідні повідомлення з прив'язаного чату співробітника **не** створюють клієнта й розмову inbox і не потрапляють до ШІ.
- Відв'язка — будь-коли з адмінки або командою в боті. Деактивація користувача відкликає прив'язку. `chat_id` не логується.
- Через який бот іде повідомлення (клієнтський бот салону чи окремий службовий) і правова підстава обробки `chat_id` працівника — відкриті питання L3 / Q13 (§7). До їх закриття Telegram-канал сповіщень вимкнено прапором поза dev; адмінка працює без нього.

### 2.10 Безпека (стисло)

| Загроза | Захист |
|---|---|
| Доступ до складу іншого tenant | RLS FORCE на всіх таблицях, композитні FK; тест крос-tenant |
| IDOR за `locationId`/`batchId`/`operationId` у scope `own` | scope закладів обчислює Application з `Actor.Access`; поза scope — 404 без розкриття |
| Витік закупівельних цін | поля відсутні без `inventory.costs`; `inventory.costs` вимагає `revenue.view = all`; `no-store`; ціни не логуються |
| Підміна історії | журнал і операції append-only (`REVOKE UPDATE, DELETE`), виправлення лише новим рухом |
| Гонки й від'ємний залишок | `FOR UPDATE` на рівні, детермінований порядок блокувань, CHECK `quantity ≥ 0` на партіях і рівнях (етап 1) |
| Подвійне проведення (дабл-клік, повтор мережі) | `Idempotency-Key` на операціях; умовний `UPDATE` статусу інвентаризації |
| Масове вивантаження | `take ≤ 200`, keyset-курсори, ліміт запису на користувача |
| ПД у Telegram власнику (етап 2) | повідомлення без ПД клієнтів, окремий gate приватності |

## 3. Consequences

**Positive**
- Облік по закладах з партіями й термінами, повна історія руху з автором і причиною, звірювана інваріантами.
- Один механізм списання (FEFO під блокуванням рівня) обслуговує ручні операції, автосписання й продаж.
- Модуль опційний: tenant без складу не бачить змін, і нічого не вмикається мовчки.
- Права вбудовано в наявну модель ADR-023 без нових механізмів; закупівельні ціни захищені на сервері.
- Собівартість і аналітика ADR-014 не змінюються: жодного ризику для наявних звітів.

**Negative / accepted trade-offs**
- Денормалізований рівень (`beauty_stock_levels`) дублює суму партій; цілісність тримається дисципліною транзакцій і тестами інваріантів, а не обмеженням БД.
- Append-only журнал не дає «виправити помилку» редагуванням: потрібні коригувальні рухи, і UI має це пояснювати.
- `inventory.costs` залежить від `beauty_analytics` через `revenue.view = all`: tenant без аналітики бачить ціни складу лише в owner.
- Переміщення миттєве: «в дорозі» товар не обліковується (Q5).
- Новий ключ прав → backfill і `catalogVersion 2`; етап 3 вимагатиме ще одного backfill (`inventory.sales`).
- У етапі 2 залишок може стати від'ємним (рішення продукту), тож звіти мають показувати дефіцит явно.
- `Down` міграції складу відмовляє, якщо журнал непорожній: відкат з даними — свідома ручна дія через gate.

## 4. Alternatives considered

- **Залишок лише як кількість на товар×заклад, без партій** — відхилено: не покриває терміни придатності й FEFO (вимога 2).
- **Залишок, що рахується лише з журналу (event sourcing без партій і рівнів)** — відхилено: FEFO потребує поточних кількостей партій, а агрегування журналу на кожен запит дороге й ускладнює блокування.
- **Лише партії без агрегованого рівня** — відхилено: немає одного рядка для `FOR UPDATE` (блокування всіх партій пари і «фантомні» нові партії), повільні списки залишків. Рівень — точка серіалізації.
- **Оптимістична конкурентність (версія рядка) замість `FOR UPDATE`** — відхилено: гарячі пари заклад×товар (популярний оксидант у етапі 2) давали б часті `409` і повтори в транзакції завершення візиту.
- **Редагований журнал / м'яке видалення рухів** — відхилено: облік товарно-матеріальних цінностей вимагає незмінної історії; прецедент `beauty_marketing_consent_events`.
- **FIFO за датою надходження** — відхилено: для косметики й фарб критичний термін, а не порядок надходження.
- **Переміщення з підтвердженням прийому («в дорозі»)** — відкладено (Q5): ускладнює облік і UI, а мережі салонів зазвичай переміщують товар у межах дня. Можна додати пізніше новим статусом операції без зміни журналу.
- **Окрема таблиця переміщень** — відхилено на користь загального заголовка операцій: та сама ідемпотентність, автор, документ і зв'язок рухів для всіх типів.
- **Вмикати модуль усім (`All`) з backfill** — відхилено: склад потрібен не всім, і модуль змінює меню й права; прецедент `beauty_marketing`.
- **Один ключ `inventory.access` з рівнями `none/view/manage`** — відхилено: не розділяє scope закладу (`own/all`) і доступ до закупівельних цін.
- **Закупівельні ціни під `revenue.costs`** — відхилено: різні модулі (`beauty_analytics` проти `beauty_inventory`) і різні люди (комірник бачить ціни надходження, але не чистий дохід). Залежність `requires revenue.view = all` зберігає ту саму межу комерційної таємниці.
- **Ключ `inventory.sales` одразу в етапі 1** — відхилено (§2.2): ключ без коду; одна зайва backfill пізніше дешевша за мертвий перемикач.
- **Блокувати візит при нестачі матеріалу / не списувати** — відхилено рішенням продукту: візит уже відбувся, облік має відображати реальність і попереджати.
- **Від'ємні партії при нестачі** — відхилено: ламає FEFO і знімок закупівельної ціни; дефіцит тримається на рівні.
- **Собівартість послуги з матеріалів замість фіксованої (ADR-014)** — не в цьому ADR (Q11): змінює семантику чистого доходу й історичних звітів; потребує окремого ADR.
- **Telegram власнику через бот ShelfGuard** — відкладено до Q13: зовнішній репозиторій і окремий потік даних між продуктами.

## 5. Scope of truth

Після `accepted` ADR-025 авторитетний для:
- модуля `beauty_inventory` і його статусу опційного (`Known`, не `All`);
- блоку прав `inventory` (ключі, рівні, обмеження, пресети, правила backfill); конкретні значення живуть у `PermissionCatalog` і §32.8, зміна **семантики** потребує нового ADR;
- моделі обліку: партії, агрегований рівень, append-only журнал і заголовок операцій, типи рухів, FEFO і правила прострочення, серіалізація через `FOR UPDATE`, заборона від'ємного залишку поза `service_consumption`;
- семантики переміщення (миттєве, дві ноги в одній транзакції) та інвентаризації (різниця до поточного рівня під блокуванням);
- принципів етапів 2–3: автосписання в транзакції завершення візиту, поведінка при нестачі, незмінність ADR-014, окремі необов'язкові поля виручки від товарів, порт `IFiscalService`;
- правил приватності Telegram-сповіщень співробітникам (§2.9).

Не авторитетний для: RLS і tenant-контексту (ADR-002), механізму прав (ADR-023), outbox (ADR-003), собівартості послуг (ADR-014), вибору фіскального провайдера (окремий ADR етапу 3). Поля, коди, ліміти й тести — контракт §32.

Потребує нового ADR: собівартість з матеріалів; переміщення «в дорозі»; ШІ-tools складу; Telegram-прив'язка для ролей, крім owner; вибір ПРРО-провайдера; мультивалютність закупівель.

## 8. Human gates

1. **Прийняття ADR-025** (схема й межа авторизації: новий блок прав і backfill).
2. **Міграція `beauty_inventory` і backfill прав на staging/prod**, будь-який `Down` там (бекап перед застосуванням; `Down` складу відмовляє за непорожнього журналу).
3. **Увімкнення модуля `beauty_inventory`** для реального бізнесу (control plane).
4. **Етап 2:** автосписання в транзакції завершення візиту (фінансово критичний потік) і окремо Telegram-прив'язка власника (L3).
5. **Етап 3:** вибір ПРРО-провайдера й юридичні вимоги (L1, L2) до прод-вмикання продажу.
6. **Мердж `integrate/*`** у base-гілку після security-review кожного етапу.
