# ADR-016: Хостинг staging (спільний сервер, Docker Compose за системним nginx) і CI/CD

**Date:** 2026-11-02 (уточнено того ж дня: спільний сервер замість окремого VPS, домен, порти, TLS; рішення gate Q1–Q7)

**Status:** accepted (2026-11-02, затвердив власник проєкту). Human gate §7 пройдено: Q1, Q2, Q3, Q4, Q5, Q7 вирішені, Q6 свідомо відкладено й staging не блокує. Відкритих блокерів рішень для staging немає; лишаються лише операційні передумови §3, які виконує людина.

**Межа дії:** ADR покриває **лише staging на спільному сервері**. Прод цим ADR **не** відкривається і потребує **окремого ADR** (хостинг, секрети, бекапи, CD). Юридичні gate ADR-010 §7.3 (R1), ADR-011 §8.3, ADR-012 §8.1, ADR-014 §8.1, ADR-015 §8.1 лишаються відкритими.

**Author:** project-architect

**Deciders:** власник проєкту. Вхідні рішення §1.2 і факти §1.4 — розмова 2026-11-02; рішення Q1–Q7 (§7) — відповіді власника в розмові 2026-11-02.

**Уточнює:**
- ADR-001 п.6 «Hosting: Docker, Vercel/ECS/Kubernetes/self-hosted»: для staging обрано self-hosted **спільний сервер** + Compose. Для проду рішення не ухвалене; прод на спільному сервері не планується без окремого ADR.
- ADR-010 §6: «Зовнішній KMS/Vault відкладено, бо хостинг не зафіксовано». Хостинг staging зафіксовано, KMS лишається відкладеним (§6).
- ADR-003: runtime-воркер (`worker/src/main.ts`) працює на DB-поллерах без Redis. Код BullMQ (`beauty-register.ts`) не підключений, тому Redis у staging немає. Якщо BullMQ підключать, потрібна правка цього ADR і окремий сервіс Redis.

Решта рішень ADR-001…015 чинна.

## 1. Контекст

### 1.1 Стан коду (перевірено 2026-11-02)
- API не застосовує міграції на старті (у `Program.cs` немає `Migrate`). Міграції застосовуються через `dotnet ef` рядком `ConnectionStrings:Migrator` від імені `beautycrm_owner`. Ця роль має NOSUPERUSER NOBYPASSRLS, і частина міграцій тимчасово знімає FORCE.
- Ролі (ADR-002, `scripts/dev/setup-db.ps1`): `beautycrm_owner` (власник, лише міграції), `beautycrm_app` (API), `beautycrm_worker` (вузька роль воркера). `DbRoleGuard` зупиняє API, якщо роль суперкористувач або BYPASSRLS.
- **Telegram polling дозволений лише в Development.** `TelegramPollingOptions.ValidateForHost` (`TelegramPolling.cs:65–72`) кидає виняток поза Development, а S3 забороняє Development на staging. Webhook `api/beauty/webhooks/{channel}/{channelId}` уже існує й перевіряє `X-Telegram-Bot-Api-Secret-Token`. `setWebhook` у коді немає, реєстрацію робить runbook (ADR-013). ADR-011: «polling локально, webhook на проді». Дедуплікація однакова для обох транспортів.
- `Channels:UseMocks=true` поза Development зупиняє старт API, тому mock-адаптер Instagram на staging недоступний.
- Ліміти частоти зберігаються в пам'яті процесу: `AiRateLimiter`, `AiKeyThrottle`, лімітери купонів і чату (review AI M2, marketing M5). Для частоти кампаній 1/7 днів є гонка між паралельними воркерами (marketing L1).
- Frontend читає `NEXT_PUBLIC_*` під час build (runbook §3), тому образ web прив'язаний до середовища.
- Юридичні gate забороняють мердж у `main` і прод. Staging-smoke у feature-гілці на синтетичних даних з тестовим ключем дозволений (ADR-010 §7.3, ADR-011 §8.3).
- **CI і деплой-артефакти (TASK-800, TASK-801):** створено `.github/workflows/ci.yml`, `.github/workflows/staging-images.yml`, Dockerfile трьох сервісів, `deploy/staging/` (Compose-шаблон, env-шаблони, `grants.sql`, README для людини), проби `/healthz` і `/readyz`. Реального запуску CI ще не було. `npm audit --audit-level=high` очищено (TASK-801). Frontend-тести в CI запускаються з `--maxWorkers=2` (нестабільність jsdom під навантаженням).
- **Борг залежностей:** транзитивні `System.Net.Http 4.3.0` і `System.Text.RegularExpressions 4.3.0` (High) у backend закрито явними версіями в `BeautyCrm.Tests.csproj` (4.3.4 / 4.3.1, TASK-802); підтвердити першим реальним прогоном CI. `bullmq`/`ioredis` у worker — мертва залежність, окрема задача (§2.5).

### 1.2 Вхідні рішення користувача
1. **Спільний сервер** (не окремий VPS): на ньому вже працює живий продакшн інших продуктів (ShelfGuard та ін.) із системним nginx. Користувач обрав саме цей варіант свідомо. Docker Compose: API, worker, web, PostgreSQL 16. Власного reverse proxy (Caddy на 80/443) немає.
2. Середовище — лише staging, прод заблоковано юридичними gate.
3. Реєстр образів — `ghcr.io`.
4. CI — GitHub Actions. PR блокують усі перевірки: frontend tsc/lint/vitest/build, worker tsc/vitest, backend `dotnet test` на реальному PostgreSQL, secret scan, dependency audit (high/critical).
5. Образи публікуються вручну (`workflow_dispatch`).
6. Деплой на сервер — лише вручну людиною (`pull` + `up`). Автоматичного CD через SSH на цей сервер немає.
7. Домен: піддомен `beauty.<DOMAIN>` (домен ShelfGuard). Один піддомен із маршрутизацією за шляхом, без окремого `api.`-піддомену.

### 1.3 Обмеження, які ADR фіксує
- ADR-001: модульний моноліт, тобто один API-процес, один worker-процес, одна БД.
- ADR-002: FORCE RLS, runtime-ролі без BYPASSRLS, `app.tenant_id`.
- ADR-003: outbox у `beauty_messages`, воркер відправляє з ідемпотентністю.
- ADR-010 §2: майстер-ключ (`Ai__Secrets__Keys__{kid}`, `Ai__Secrets__ActiveKeyId`) зберігається поза БД, образом, `appsettings*.json` і репозиторієм. Його бекап зберігається окремо від бекапу БД.

### 1.4 Факти про сервер (перевірено користувачем 2026-11-02)
Конкретні адреси, порти SSH, облікові дані — лише в приватних нотатках людини, не в репозиторії.
- **DNS:** A-запис `beauty.<DOMAIN>` створено, публічні резолвери його повертають.
- **Порти провайдера:** зовнішній 443 провайдер направляє на внутрішній 8443 системного nginx (сертифікат валідний); зовнішній 80 відкритий; 8443 ззовні закритий (очікувано). Публічна адреса — `https://beauty.<DOMAIN>` **без порту**. Додатковий порт у провайдера не потрібен.
- **TLS:** чинний сертифікат ShelfGuard виданий лише на корінь домену, піддомену в ньому немає. На сервері є certbot, автопоновлення працює через `certbot.timer`.
- **Порти хоста:** вільні 5200 (API) і 3400 (web). Зайняті: 3000, 3001, 3010, 3100, 3200, 3300, 5100, 5110, 5432–5435, 6379–6381, 1883/1884, 8001, 8443, 10048. Стан змінюється, перед кожним `up` звіряти `ss -ltn`.

## 2. Рішення

### 2.1 Топологія (один Compose-проєкт `beauty_staging` за системним nginx)
| Сервіс | Образ | Публікація на хості | Примітки |
|---|---|---|---|
| системний nginx | наявний, **не** частина Compose | 8443 (зовн. 443), 80 | Новий окремий server-блок для `beauty.<DOMAIN>` (§2.1.2). Чужі server-блоки не змінюються. |
| `web` | `ghcr.io/<owner>/beautycrm-web:sha-<git>` | `127.0.0.1:3400` | Next.js standalone. `NEXT_PUBLIC_*` (build-arg `public_origin`) = `https://beauty.<DOMAIN>`. `API_URL` = внутрішня адреса `api`. |
| `api` | `ghcr.io/<owner>/beautycrm-api:sha-<git>` | `127.0.0.1:5200` | `ASPNETCORE_ENVIRONMENT=Staging`. Роль `beautycrm_app`. `Beauty__TrustedProxies` = шлюз мережі `beauty_staging` (адреса, з якої контейнер бачить nginx; не вся підмережа). `Beauty__AllowedOrigins=https://beauty.<DOMAIN>`. |
| `worker` | `ghcr.io/<owner>/beautycrm-worker:sha-<git>` | — | Роль `beautycrm_worker` (не `beautycrm_app`, review reminders M4). |
| `db` | `postgres:16.x`, закріплена мінорна версія | **немає** | Власний контейнер, том `beauty_staging_pgdata`. Лише internal-мережа. Адміністрування — `docker compose exec` людиною. |

Для всіх сервісів: `restart: unless-stopped`, healthcheck, ротація логів (`json-file`, обмежений `max-size`/`max-file`), ліміти `mem_limit`/`cpus`, non-root, `no-new-privileges`, `cap_drop: ALL` і `read_only` для api/worker/web. Образи не містять секретів і `appsettings.*` з секретами.

#### 2.1.1 Ізоляція на спільному сервері (обов'язково)
- **Імена:** проєкт, контейнери, мережі й томи мають префікс `beauty_staging`. Мережі: `beauty_staging` (вихід в інтернет, фіксована вільна `/24`) і `beauty_staging_db` (internal, без виходу). Підмережа не перетинається з наявними docker-мережами.
- **БД:** лише власний PostgreSQL-контейнер. Чужі БД, Redis, MQTT і мережі не використовуються й не підключаються.
- **Порти:** лише `127.0.0.1`, нестандартні вільні значення (§1.4). Порт БД не публікується.
- **Ресурси:** ліміти mem/cpu на кожен сервіс (орієнтир у `deploy/staging/README.md`), щоб staging не витісняв чужий продакшн.
- **Дії на сервері:** кожну дію (створення каталогів, `up`, правка nginx, certbot, cron) виконує людина і схвалює **окремо**. Агенти й CI на сервер не заходять. Заборонені глобальні команди Docker (`system/network/volume prune`, масове видалення контейнерів).
- **Перспектива:** перед продом staging (і тим паче прод) винести на окремий сервер. Прод на спільному сервері не планується без окремого ADR.

#### 2.1.2 Публікація назовні: домен, маршрутизація, TLS
- **Один піддомен** `beauty.<DOMAIN>`, маршрутизація за шляхом у новому server-блоці nginx (`listen 8443 ssl`, `server_name beauty.<DOMAIN>`; розрізнення за SNI/`server_name`, сусідні сайти не зачіпаються):
  - `/api/platform/` → API, лише allowlist IP оператора (або закрито повністю);
  - `/api/session/` → web (route handlers Next);
  - решта `/api/` (включно з webhook-ами каналів) → API;
  - усе інше → web.
  Одне походження прибирає CORS і спрощує cookie. Заголовки `X-Forwarded-*` nginx **перезаписує**, клієнтським не довіряє. Еталонний приклад — `deploy/staging/README.md` §6.
- **Доступ до staging-вебу (Q5):** увесь server-блок закрито **basic auth** у nginx (`auth_basic`, htpasswd створює людина на сервері). Поза basic auth (`auth_basic off`) лишаються лише маршрути, потрібні боту й застосунку: webhook-и каналів `/api/beauty/webhooks/` (захист — secret token) і `/api/session/` (захист — застосунок), як у `deploy/staging/README.md` §6.3/§6.5. IP allowlist для вебу не використовується; окреме обмеження `/api/platform/` вище не змінюється.
- **На порту 80** для `beauty.<DOMAIN>`: лише ACME HTTP-01 challenge і редирект на `https://`.
- **Сертифікат:** **новий** сертифікат Let's Encrypt саме для `beauty.<DOMAIN>` (certbot, HTTP-01 через відкритий 80). Чинний сертифікат ShelfGuard не розширюється й не перевидається. Випуск — крок людини з sudo на сервері; certbot не повинен редагувати чужі server-блоки (`certonly`, webroot або nginx-плагін без запису в конфіг). Поновлення — наявний `certbot.timer` (після випуску перевірити `certbot renew --dry-run`).
- Заголовки: HSTS, `X-Robots-Tag: noindex, nofollow`, `server_tokens off`, обмеження розміру тіла. Зміни nginx: лише новий файл, `nginx -t` перед кожним reload.

### 2.2 Рівно один інстанс кожного сервісу
`api` і `worker` мають по одній репліці. `deploy.replicas > 1` і `docker compose up --scale` заборонені. Причини: in-memory лімітери (S4), гонка частоти кампаній (L1). Оновлення означає короткий простій (stop → start), для staging прийнятно. Lease polling у БД захищає від перекриття процесів під час перезапуску, але не робить безпечними кілька реплік.

### 2.3 Транспорт Telegram на staging: webhook (вирішено, Q1)
- **Рішення — webhook на 443.** Telegram приймає webhook лише на портах 443/80/88/8443; публічний 443 доступний (§1.4), тому URL — `https://beauty.<DOMAIN>/api/beauty/webhooks/telegram/{channelId}` без порту. Змін коду не потрібно, guard polling лишається недоторканим, staging відтворює цільову схему проду (ADR-011).
- `setWebhook` із `secret_token` (= `WebhookSecret` каналу) і `allowed_updates=["message","callback_query"]` виконує людина окремим кроком за `deploy/staging/README.md` §2.1 (ADR-013).
- **Polling на staging не вмикається** (`Channels__Telegram__Polling__Enabled=false`; код забороняє його поза Development). Варіант «дозволити polling у `Staging`» відхилено (§5).
- Потрібен **окремий тестовий бот** із власним токеном: один токен не можна ділити між dev-polling і staging-webhook (`getUpdates` отримає 409 Conflict, а webhook перехопить оновлення dev).
- Ціна: публічний вхідний endpoint; webhook-шлях ще не проганявся в dev-smoke, тож потрібен QA-прогін.

### 2.4 Образи й реєстр
- Три образи (`beautycrm-api`, `beautycrm-worker`, `beautycrm-web`) у `ghcr.io`, пакети **приватні**.
- Тег — повний git SHA (`sha-<40>`). Рухомий тег `staging` лише інформаційний, деплой іде **за digest**.
- Публікує `staging-images.yml` (`workflow_dispatch`, вхідні `ref`, `public_origin`). Оскільки мердж у `main` заблоковано, staging збирається з feature- або `integrate/*`-гілки. Перед публікацією workflow перевіряє, що для цього SHA пройшли всі обов'язкові CI-перевірки: обхід PR-перевірок через ручний запуск заборонений.
- Права: `packages: write` має лише publish-workflow, у решти `contents: read`. Публікує `GITHUB_TOKEN`, PAT не потрібен. На сервері — `docker login` токеном лише `read:packages`, який створює і зберігає людина.

### 2.5 CI (кожен PR, усі перевірки обов'язкові)
| Перевірка | Команда (орієнтир) |
|---|---|
| frontend | `npx tsc --noEmit`, `npm run lint`, `npm test -- --maxWorkers=2` (vitest), `npm run build` |
| worker | `npm run build` (tsc --noEmit), `npm test` (vitest) |
| backend | `dotnet test backend` з `BEAUTY_TEST_REQUIRE_DB=1` на реальному PostgreSQL 16 (Testcontainers). Без БД тест має падати, а не пропускатися |
| secret scan | gitleaks, закріплена версія; перший запуск — по всій історії |
| dependency audit | `npm audit --audit-level=high` (frontend, worker); `dotnet list package --vulnerable --include-transitive`, падіння на High/Critical |

- Required status checks у branch protection `main` налаштовує людина в GitHub **перед першим розгортанням з `main`** (Q6, відкладено свідомо). Staging з feature- або `integrate/*`-гілки цього не потребує; обхід перевірок закриває publish-workflow (§2.4).
- Гігієна: `pull_request`, а не `pull_request_target`. У PR-workflow немає секретів. Actions закріплені за SHA. Для PR налаштовано `concurrency`.
- Винятки аудиту фіксуються у файлі allowlist (ID, причина, строк дії, хто схвалив) і лише за схваленням людини (власника, Q6).
- **Очікуваний стан першого запуску:** транзитивні High у backend закрито (TASK-802, §1.1), backend-аудит має пройти; якщо ні — виправлення окремою задачею або тимчасовий виняток через allowlist зі схваленням людини. Видалення `bullmq`/`ioredis` з worker — окрема задача, на CI не впливає.

### 2.6 Деплой — лише вручну
Етапи: (1) CI + ручна публікація образів; (2) **ручний деплой людиною** на сервері: `docker compose pull` + `up -d` за digest-ами з `.env.compose`. Автоматичний CD через SSH на спільний сервер **не планується**: SSH-ключ до хоста з чужим продакшном у GitHub розширив би радіус ураження на сторонні продукти. Автоматичний CD можна розглянути лише після переїзду на окремий сервер (правка цього ADR).

### 2.7 Секрети: варіанти й рішення (Q2)
| Критерій | **A. Файли на сервері (600)** | B. GitHub Environments → сервер під час CD | C. A + docker secrets (`/run/secrets`) |
|---|---|---|---|
| Де зберігаються | лише сервер | GitHub + сервер | лише сервер |
| Потрібен CD/SSH-ключ у GitHub | ні | так (на спільному сервері неприйнятно, §2.6) | ні |
| Радіус ураження | компрометація сервера | сервер + GitHub-акаунт або будь-який workflow з доступом до environment | сервер |
| Видно в `docker inspect` | так | так | ні |
| Аудит змін | немає | журнал GitHub | немає |
| Зміни коду | ні | ні | так (key-per-file / `*_FILE` для API й worker) |

**Рішення: A** (Q2 вирішено). Секрети створює й записує на сервері лише людина; через чат, тікети, CI чи агентів вони не передаються. SSH-доступ до сервера має лише людина (власник); окремий deploy-користувач — рекомендація (§2.11), не передумова.
- Окремий env-файл для кожного сервісу (`api.env`, `worker.env`, `db.env`), режим `600`, каталог `700` поза git-клоном. Кожен контейнер отримує лише свої змінні.
- Секрети в env: `ConnectionStrings__Default` (пароль app), `WORKER_DATABASE_URL` (пароль worker), `Auth__JwtSigningKey`, `Auth__PlatformKey`, `Channels__EncryptionKey`, `Ai__Secrets__Keys__{kid}` + `Ai__Secrets__ActiveKeyId` (лише API), `POSTGRES_PASSWORD` (лише `db`). Токен бота й ключ ШІ tenant зберігаються в БД зашифрованими (ADR-010, канали).
- Пароль `beautycrm_owner` і `ConnectionStrings__Migrator` — в окремому `migrator.env` (`600`, поза клоном), не підключеному до жодного постійного сервісу. Лише для разового застосування міграцій і `ai-secrets reencrypt` (S5).
- Значення генерує людина на сервері (`openssl rand`), вони відрізняються від dev. Зашифрована копія env-файлів і майстер-ключа зберігається у власника **окремо** від дампів БД (S1), наприклад у його менеджері паролів.
- B не застосовується (немає автоматичного CD). C — подальше посилення (задача на код), не блокер staging.

### 2.8 БД, ролі, міграції
- Ролі як у dev: `beautycrm_owner`, `beautycrm_app`, `beautycrm_worker`, усі NOSUPERUSER NOBYPASSRLS. Суперкористувач `postgres` використовується лише для bootstrap, GRANT-ів і бекапу всередині контейнера; через мережу хоста він недоступний.
- **Міграції застосовуються лише через human gate і лише після свіжого бекапу (Q7 вирішено).** SQL кожної міграції схвалює людина (власник) перед застосуванням; простій `api`/`worker` на час міграції на staging прийнятний. Порядок:
  1. publish-workflow додає артефакт `dotnet ef migrations script --idempotent` для цього SHA;
  2. людина переглядає SQL (блокування `ACCESS EXCLUSIVE`, втрати даних у Down, review reminders I6) і схвалює;
  3. людина робить обов'язковий окремий передміграційний дамп (§2.9) і перевіряє, що файл створено;
  4. зупиняє `api` і `worker` (простій прийнятний), застосовує скрипт через `psql` від імені `beautycrm_owner`;
  5. застосовує `deploy/staging/db/grants.sql`: GRANT для app/worker, `REVOKE UPDATE, DELETE ON beauty_ai_settings_audit` (S2), REVOKE на журнал згод (marketing M3), точкові права воркера;
  6. запускає нові образи і робить smoke.
- Автоміграцій на старті API немає й не буде (owner-рядок ніколи не потрапляє в runtime).

### 2.9 Бекапи (мінімум, Q3 вирішено)
- Щоденний `pg_dump -Fc` через `docker compose exec -T db pg_dump -U postgres` (cron/systemd timer на хості — дія людини).
- Плюс **обов'язковий окремий дамп перед кожною міграцією** (§2.8 крок 3); щоденний дамп його не замінює.
- **Не від імені `beautycrm_owner`.** Через FORCE RLS дамп від owner або падає (`row_security=off`), або з `--enable-row-security` **мовчки вивантажує порожні таблиці**. Тому потрібен суперкористувач або окрема BYPASSRLS-роль лише для читання. `--enable-row-security` заборонено.
- Дамп шифрується на хості (`age` або gpg) публічним ключем. Приватний ключ зберігається в людини (власника) офлайн, на сервері його немає.
- Дампи зберігаються **локально** на сервері в каталозі `700` поза клоном: щоденні — **14 днів**, плюс **ліміт місця** (старіші видаляються, щоб не заповнити спільний диск; моніторинг диска — §2.11).
- **Копія поза сервером відкладена** (§6) і не блокує staging. Прийнятий ризик: втрата сервера означає втрату й дампів; для staging на синтетичних даних це допустимо.
- Раз на місяць (і перед першою міграцією) дамп перевіряється відновленням у тимчасовий контейнер без публікації портів + smoke.
- Бекап env-файлів і майстер-ключа зберігається окремо від дампів (S1, §2.7).
- RPO ≈ 24 год (випливає з щоденного дампу; перед міграцією — свіжий дамп). RTO для staging не фіксується як зобов'язання (орієнтир — кілька годин ручного відновлення).

### 2.11 Хост (спільний, не під нашим контролем)
ОС, firewall, системний nginx і Docker-демон належать спільному серверу; staging їх не переналаштовує. Рекомендації власнику сервера (значення лише в приватному сховищі людини, не в нотатках відкритим текстом і не в репозиторії):
- змінити поточний пароль SSH (наразі він зберігається в нотатках відкритим текстом) і більше не зберігати паролі в нотатках;
- вхід лише за SSH-ключем, без пароля й без прямого входу root;
- окремий deploy-користувач із мінімальними правами замість адміністратора (рекомендація, не передумова; наразі SSH-доступ має лише власник, Q2). Членство в групі `docker` еквівалентне root на хості (зокрема щодо чужого продакшну), тому коло таких користувачів мінімальне, а sudo для nginx/certbot — лише людині-адміністратору;
- моніторинг вільного диска й навантаження після запуску staging.

## 3. Передумови запуску staging
Обов'язкові умови з `docs/reviews/security-review-ai-settings-2026-10.md` (повторено в chat-assistant review):
- **S1.** Майстер-ключ лише в секретах середовища (§2.7, файл 600), не в репозиторії, образі, `appsettings*.json`. Бекап ключа окремо від БД.
- **S2.** Після міграції `REVOKE UPDATE, DELETE ON beauty_ai_settings_audit FROM beautycrm_app` (§2.8 крок 5).
- **S3.** `ASPNETCORE_ENVIRONMENT` не Development, `Ai:UseMockProvider=false`.
- **S4.** Один інстанс API (§2.2).
- **S5.** Платформний ключ вимкнений до рішення R1. `ConnectionStrings:Migrator` лише для разового CLI `ai-secrets reencrypt` (§2.7).

Додатково (рішення ухвалено, §7.1; нижче — операційні кроки людини на сервері):
- Воркер працює під `beautycrm_worker` (reminders M4).
- Закрито M2/M3 reminders, якщо вмикаються нагадування й відгуки.
- Маркетинг вимкнений до закриття H1/M2/M3 і QA TASK-786.
- Окремий тестовий бот створено; `setWebhook` виконано людиною за `deploy/staging/README.md` §2.1, `getWebhookInfo` без помилок (Q1, §2.3).
- Випущено сертифікат для `beauty.<DOMAIN>`, додано окремий server-блок nginx із basic auth (webhook і `/api/session/` поза ним), `nginx -t` чистий (§2.1.2, Q5).
- Env-файли (`600`, поза клоном) і `migrator.env` створено людиною на сервері (§2.7, Q2).
- Щоденний шифрований дамп налаштовано (14 днів, ліміт місця) і один раз перевірено відновленням до першої міграції (§2.9, Q3).
- CI один раз реально пройшов (або виняток аудиту схвалено людиною, §2.5). Branch protection `main` для staging з feature-гілки не потрібен (Q6).

## 4. Наслідки
Позитивні:
- Без нового сервера й нових витрат; використовуються наявні nginx, certbot і автопоновлення.
- Одне походження (`https://beauty.<DOMAIN>`, без порту) — без CORS і без окремого сертифіката для API.
- Вимоги ADR-002 і ADR-010 до ролей і майстер-ключа виконуються без нової інфраструктури.
- Compose-файл і образи переносні: переїзд на окремий сервер або прод-рішення (окремий ADR) їх перевикористає.
- CI блокує регресії й витоки секретів до мерджу.

Негативні / прийняті компроміси:
- **Спільна доля з чужим продакшном.** Падіння, перевантаження чи обслуговування сервера зачіпає і staging, і сторонні продукти. Staging залежить від чужої конфігурації nginx і маппінгу портів провайдера (443 → 8443).
- **Єдина точка відмови.** Дампи поки лише локальні (§2.9): втрата сервера означає втрату staging-даних (синтетичних); відновлення — інший сервер + seed або дамп, якщо копію зроблено вручну, + env-файли від власника.
- Оновлення з простоєм. Горизонтального масштабування немає (in-memory лімітери).
- Секрети у відкритому вигляді на диску спільного сервера і в `docker inspect`; адміністратори хоста й члени групи `docker` мають до них доступ. Значення staging ніколи не використовуються в інших середовищах.
- Усі кроки на сервері ручні (деплой, міграції, certbot, nginx, `setWebhook`) — ризик людської помилки; їх описано в `deploy/staging/README.md`.
- Образ web прив'язаний до `https://beauty.<DOMAIN>` (build-time `NEXT_PUBLIC_*`). Для проду потрібна окрема збірка.
- Суворий dependency audit блокуватиме PR при кожній новій High/Critical вразливості до виправлення або схваленого людиною винятку (§2.5).
- Через заблокований `main` staging збирається з неосновної гілки, тож його стан може розходитися з `main`.

### 4.1 Ризики для чужого продакшну (окремо)
| Ризик | Пом'якшення |
|---|---|
| Помилка в nginx ламає сусідні сайти при reload | Лише новий файл; `nginx -t` перед reload; чужі server-блоки не редагуються; розрізнення за `server_name` |
| certbot змінює чужий сертифікат або чужі server-блоки | Окремий сертифікат лише для `beauty.<DOMAIN>`, `certonly`; чинний сертифікат не розширюється |
| Конфлікт портів або підмереж Docker | Лише `127.0.0.1`, перевірені вільні порти (5200/3400); вільна `/24`; звірка `ss -ltn` і `docker network inspect` перед `up` |
| Staging витісняє ресурси (RAM/CPU/диск) | `mem_limit`/`cpus`, ротація логів, обмеження локальних дампів, `docker stats` після запуску |
| Випадкове видалення чужих контейнерів/томів/мереж | Префікс `beauty_staging`, команди лише з `-f docker-compose.staging.yml`, заборона глобальних `prune`/масового `rm` |
| Компрометація staging (публічний webhook, web) переходить на хост і чужі продукти | Non-root, `cap_drop: ALL`, `read_only`, `no-new-privileges`; БД в internal-мережі; `/api/platform/` за allowlist; basic auth на web (Q5); без SSH-ключів у GitHub (§2.6); hardening SSH (§2.11) |
| Компрометація чужого продукту розкриває секрети staging | Лише синтетичні дані й тестові ключі; секрети staging унікальні; винесення на окремий сервер перед продом (§2.1.1) |

### 4.2 Інші ризики
- Webhook — публічний endpoint без rate limit на рівні nginx. Додати `limit_req` у server-блок або ліміт в API окремою задачею.
- Публічний staging може бути знайденим. Web закрито basic auth (Q5, §2.1.2) плюс `noindex`. Webhook-шлях і `/api/session/` лишаються поза basic auth (захист — secret token і застосунок). Пароль basic auth — спільний статичний секрет; його зберігає власник і змінює при підозрі на витік.
- Помилка в процедурі бекапу (дамп від owner) дає порожні бекапи, яких ніхто не помічає. Пом'якшення — обов'язкова перевірка відновленням.
- CI ще не запускався: можливі розбіжності між локальними й runner-середовищами (зокрема jsdom-тести). Перший прогін — окремий крок перевірки.

## 5. Альтернативи
- **Окремий VPS з власним Caddy на 80/443 (початковий варіант)** — відхилено рішенням користувача на користь спільного сервера (без нових витрат, з наявними DNS/TLS). На спільному сервері 80/443 тримає системний nginx, тому власний proxy на цих портах неможливий без втручання в чужий продакшн. Лишається рекомендованим напрямом перед продом (§2.1.1).
- **Окремий піддомен `api.`** — відхилено. Потрібні ще один DNS-запис і сертифікат, CORS і cross-site cookie; маршрутизація за шляхом на одному походженні простіша.
- **Розширити чинний сертифікат ShelfGuard на піддомен** — відхилено. Зачіпає артефакт чужого продукту й зв'язує їхні поновлення/відкликання.
- **Polling для Telegram на staging** — відхилено (Q1): потребує зміни guard у коді й security-review, а webhook доступний через 443 (§2.3).
- **IP allowlist замість basic auth для web** — відхилено рішенням власника (Q5); basic auth уже є в шаблоні nginx і не прив'язаний до IP оператора.
- **Копія бекапів поза сервер (S3) як передумова staging** — не обрано зараз (Q3): відкладено (§6), для синтетичних даних достатньо локальних шифрованих дампів.
- **PaaS (Azure App Service/Container Apps, Railway, Render)** — відхилено зараз. Керований PostgreSQL часто обмежує ролі й RLS-налаштування (суперкористувач, BYPASSRLS-роль для бекапу), поллери вимагають постійно запущеного процесу, а прив'язка до провайдера з'являється до вибору юрисдикції проду. Можна переглянути для проду.
- **Kubernetes (керований або k3s)** — відхилено. Операційна складність непропорційна одному інстансу; репліки недоступні через in-memory лімітери.
- **systemd без контейнерів** — відхилено. Потрібні .NET, Node і PostgreSQL на спільному хості (ризик для сусідів), немає незмінних артефактів і відкату за digest.
- **Автоматична публікація образів на кожен push** — відхилено. Користувач обрав ручну публікацію; автопублікація з feature-гілок під юридичними gate небажана.
- **Автоматичний CD через SSH** — відхилено для спільного сервера (§2.6).
- **Автоміграції на старті API** — відхилено. Порушує human gate і вимагає owner-рядка в runtime.

## 6. Відкладено
- Винесення staging на окремий сервер (рекомендовано перед продом).
- Прод-середовище (окремий ADR після закриття юридичних gate; не на спільному сервері).
- Горизонтальне масштабування: спершу перенести лімітери в БД/Redis і прибрати L1-гонку.
- Зовнішній секрет-менеджер / KMS (ADR-010 §6); docker secrets (варіант C).
- Копія дампів поза сервером (S3-сумісне сховище в іншого провайдера, облікові дані лише на запис, versioning/object lock) — Q3; не блокує staging.
- Branch protection `main` з required checks §2.5 — до першого розгортання з `main` (Q6).
- Окремий deploy-користувач на сервері (§2.11).
- Автоматичний CD (лише після переїзду на окремий сервер).
- Rate limit для webhook на рівні nginx/API.
- Централізовані логи, метрики, алерти. Сканування образів (Trivy) — бажано, не блокер.
- Борг залежностей: видалення `bullmq`/`ioredis` з worker.

## 7. Питання human gate

### 7.1 Вирішені
- **Q4 — сервер і домен.** Спільний сервер із наявним nginx (не окремий VPS), піддомен `beauty.<DOMAIN>` з одним походженням; DNS створено, 443/80 доступні, сертифікат — новий Let's Encrypt (§1.4, §2.1.1, §2.1.2). Джерело: розмова з користувачем 2026-11-02.
- Джерело Q1–Q3, Q5–Q7 нижче: відповіді власника в розмові 2026-11-02.
- **Q1 — транспорт Telegram.** Webhook на 443 (`https://beauty.<DOMAIN>`, без порту); polling не вмикається; окремий тестовий бот; `setWebhook` виконує людина за `deploy/staging/README.md` (§2.3).
- **Q2 — секрети.** Варіант A: окремі env-файли `600` на кожен сервіс поза клоном; `migrator.env` окремо, не підключений до постійних сервісів. Секрети створює людина на сервері, не через чат. SSH-доступ — лише власник; окремий deploy-користувач — рекомендація (§2.7, §2.11).
- **Q3 — бекапи.** Щоденний локальний шифрований дамп (`pg_dump` від `postgres` у контейнері), зберігання 14 днів і ліміт місця, плюс обов'язковий окремий дамп перед кожною міграцією. Копія поза сервером відкладена, не блокує staging (§2.9, §6).
- **Q5 — доступ до web.** Basic auth у nginx; webhook-и каналів і `/api/session/` поза basic auth (як у README); IP allowlist для вебу не використовується (§2.1.2).
- **Q7 — міграції.** SQL кожної міграції схвалює людина перед застосуванням; простій на staging прийнятний (§2.8).

### 7.2 Свідомо відкладені (не блокують staging)
- **Q6 — GitHub.** Branch protection `main` з required checks §2.5 налаштовується перед першим розгортанням з `main` (staging з feature-гілки не блокує). Винятки dependency audit схвалює людина. Пакети ghcr — приватні (§2.4, §2.5).

### 7.3 Відкриті
Немає відкритих питань, що блокують staging. Прод — окремий ADR (див. Status).

## 8. Scope of truth
Цей ADR авторитетний **лише для staging на спільному сервері**: топології staging, ізоляції на спільному сервері, публікації назовні, маршрутизації, TLS і basic auth (§2.1, §2.1.1, §2.1.2), обмеження «один інстанс» (§2.2), транспорту Telegram на staging (§2.3), реєстру й тегування образів (§2.4), складу обов'язкових CI-перевірок (§2.5), моделі деплою (§2.6), моделі секретів staging (§2.7), процедури міграцій і бекапів на staging (§2.8–2.9), прапорців staging (§2.10), вимог до спільного хоста (§2.11). Конкретні файли (`.github/workflows/*`, `deploy/*`, `Dockerfile`) мають відповідати цьому ADR. Розбіжність — дефект файлу, а не тихе рішення. Зміна хостингу (зокрема переїзд з/на спільний сервер), кількості інстансів, моделі секретів або процедури міграцій потребує нового ADR. Для проду цей ADR не авторитетний: прод потребує окремого ADR.
