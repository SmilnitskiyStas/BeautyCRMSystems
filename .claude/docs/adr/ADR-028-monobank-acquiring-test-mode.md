# ADR-028: Оплата замовлень товарів через monobank acquiring (тестовий режим)

- **Статус:** proposed (реалізовано в гілці; вмикання на staging - human gate)
- **Дата:** 2026-11-22
- **Пов'язані:** ADR-026 §2.7 (оплата замовлень, `IPaymentService`), A3 у CLAUDE.md (провайдер не обрано), контракт §33.7, §33.23

## 1. Контекст

`IPaymentService` має лише mock. Користувач обрав monobank acquiring («Plata by mono»), спершу **лише тестове середовище** і **лише
замовлення товарів у мобільному застосунку**; передоплата запису лишається на mock. API monobank (api.monobank.ua/docs/acquiring.html)
працює через рахунок: `POST /api/merchant/invoice/create` -> `pageUrl`, клієнт платить на сторінці банку, статус приходить вебхуком
(POST з `X-Sign` - ECDSA над тілом, до 3 спроб, порядок не гарантовано, `expired` вебхуком не шлеться) і читається
`GET /api/merchant/invoice/status`. Тестове середовище - той самий хост з тестовим токеном; картка - будь-яка валідна за Луном.

## 2. Рішення

1. **Провайдер обирається конфігом:** `Payments:Provider = mock | monobank` (за замовчуванням `mock`). Для `monobank`:
   `Monobank__Token` - лише секрет/змінна середовища; `Monobank:TestMode=true` **обов'язково** (інакше помилка старту: живий режим
   у цьому релізі заборонено); `Monobank:PublicBaseUrl` (https) - з нього будуються `webHookUrl` і `redirectUrl`.
2. **Рахунок замість синхронного списання.** `PaymentResult` отримав `Pending` + `CheckoutUrl` (адитивно). P4: claim як у ADR-026 ->
   `ChargeAsync` створює рахунок (`reference` = `PaymentId:N`, сума в копійках, `validity` = `Monobank:InvoiceValiditySeconds`, 300 с) ->
   id рахунку пишеться в `beauty_payments.provider_payment_id` (`provider = monobank`, без міграції) -> `200 {order, paymentUrl}`,
   замовлення - «оплата в процесі» (claim тримає товар і блокує скасування/TTL).
3. **Ідемпотентність за PaymentId.** Повторний `ChargeAsync` того самого `PaymentId` (reconcile після `PaymentStaleSeconds`, дія CRM)
   не створює другий рахунок, а читає статус наявного: `success` -> фіналізація; `failure|expired|reversed` -> явна відмова
   (claim знімається, спробу можна повторити новим рахунком); `created|processing|hold` -> лишається «в процесі».
4. **Вебхук** `POST /api/public/{tenantSlug}/payments/monobank/webhook`: tenant - зі шляху (його задає наш `webHookUrl`), автентичність -
   лише підпис (ключ `GET /api/merchant/pubkey` кешується; при невдачі перезапит не частіше разу на хвилину). Невалідний підпис -> 401.
   Після валідного підпису - завжди 200. Повідомлення - лише тригер до тих самих CAS-переходів (`FinalizePaidAsync` /
   `MarkPaymentFailedAsync` за чинним claim); перевіряються збіг `invoiceId` з платежем і суми. Повтор/перестановка/гонка з reconcile
   безпечні. Гроші, що прийшли на вже закрите замовлення, повертаються (лог `product_order_payment_orphan`).
5. **Повернення** (компенсація нестачі, скасування адміном): `POST /api/merchant/invoice/cancel` з `extRef = PaymentId:N`; рахунок у
   статусі `reversed` = уже повернено (повтор безпечний). Платежі з `mock_*` (до перемикання) і записи повертає mock.
6. **Застосунок** відкриває `paymentUrl` у системному браузері; банк повертає на `GET /api/public/payments/return` (сторінка без стану,
   веде на `beautycrm://order`); застосунок опитує P3 і перепитує сервер при поверненні на передній план. `payments` - зарезервований slug.

## 3. Наслідки

- Плюс: реальний потік оплати на staging без нових таблиць; mock лишається за замовчуванням, тести/dev без змін.
- Мінус: якщо клієнт закрив сторінку банку, замовлення лишається «в процесі» до закінчення рахунку (≤ 5 хв) + reconcile (P4 після
  `PaymentStaleSeconds` або «Перевірити оплату» в CRM); фонового reconcile немає (як ADR-026 §2.7 п.5).
- Один merchant-токен на інсталяцію: гроші всіх tenant ідуть на один рахунок. Для тесту прийнятно; **для продакшну потрібні токени
  на tenant** (зберігання секретів, онбординг мерчанта) - окремий ADR разом з ПРРО (`merchantPaymInfo` з кошиком) і офертою.
- Передоплата запису на monobank - окрема задача (`BookingService` списує синхронно; потрібен стан «очікує оплати» для запису).

## 4. Альтернативи

- Токенізація картки / оплата за реквізитами - потребує PCI DSS або окремого підключення в monobank; відхилено.
- Опитування статусу без вебхука - затримка й навантаження; вебхук + reconcile як резерв.
